# 图表点击下钻技术方案

> 对应《LLM + MCP 富可视化流式响应技术方案》第二阶段"Drill Down / 图表点击"。
> 前置：第一阶段最小闭环已完成（四类渲染器 + SSE 交错流 + ResultStore）。

---

## 1. 目标与非目标

**目标**：用户点击统计图中的某个类目（如柱状图的"北京"），对话自动发起针对该类目的深入分析（如"展示 person-001 在北京的活动明细"），结果以文字 + 时间线/表格继续呈现在对话流中。

**非目标**：
- 不做图表**原地变换**（柱状图某根柱子展开成子图）——那是纯前端交互，与对话式分析的目标形态不符
- 不让前端自行取数计算——数据永远来自 MCP 工具（铁律一：LLM/前端不搬运数据）

## 2. 核心设计：下钻 = 一次自动发起的对话

下钻的本质是**前端把用户在图上的点击翻译成一句追问**，走现有对话链路：

```
用户点击柱子"北京"
   │
   ▼
前端组装追问: "深入分析 person-001 在北京的活动"
   │                                    ┌─ 来自哪里？见 §4
   ▼                                    │
sendMessage(追问) ──► agent-client ──► LLM ──► kg_list_activity(personId, 北京过滤)
                       （完全复用现有链路）          │
                                                    ▼
                                       文字 + Timeline/Table 继续流式输出
```

**为什么这样设计**：
1. 零新协议——LLM 自己理解"下钻意图"并选择工具（这正是方案 §4.3 LLM 的职责）
2. 下钻语义由数据提供方的 ViewHint 声明（见 §3），前端不猜
3. 复用 parts 模型，下钻结果自然接续在对话流中

## 3. 前端怎么知道要下钻：ViewHint 增加 drillDown 声明

**关键决策：下钻能力与提示由 MCP 工具（数据提供方）在 ViewHint 中声明**，符合方案"数据提供方知道自己数据适合怎样被使用"的原则。

### 3.1 schema 扩展（mcp-result.schema.json）

```json
{
  "id": "city-stat",
  "type": "chart",
  "subType": "bar",
  "title": "各城市活动次数",
  "mapping": { "category": "city", "value": "count" },
  "drillDown": {
    "enabled": true,
    "label": "深入分析该城市",
    "dimension": "city",
    "promptTemplate": "深入分析 {personId} 在 {city} 的活动情况，展示活动明细"
  }
}
```

字段语义：

| 字段 | 说明 |
|---|---|
| `enabled` | 是否可下钻。false/缺省 = 点击无动作 |
| `label` | 悬停提示文案（可省略，默认"深入分析"） |
| `dimension` | 点击命中的数据维度（= mapping.category 等），前端用于从被点的行提取值 |
| `promptTemplate` | 追问模板，`{占位符}` 会被替换 |

### 3.2 占位符取值规则（前端，确定性的）

模板占位符的值**全部来自被点击的数据行 + surface 上下文**，不经过 LLM：

```
{city}      ← 被点击行的 row[mapping.category]（即 dimension 字段值）
{count}     ← 被点击行的 row[mapping.value]
{任意字段}   ← 被点击行的同名字段
{personId}  ← 特殊：从 resultMeta.attributes 或 data 行中取（见 §4.2）
```

前端做纯字符串替换，无猜测。

## 4. 下钻的数据从哪里来：三层来源

### 4.1 追问上下文（本次点击的即时数据）

被点击的行数据。前端在 ChartRenderer 点击回调中拿得到（ECharts `params.data` / 通过 encoding 反查 row）。这解决 `{city}` 等占位符。

### 4.2 查询主体（"谁"的活动：personId 等父级参数）

这是关键难点：图表数据是 `[{city, count}]`，**personId 不在行数据里**（它是查询参数不是结果字段）。两个来源：

**来源 A（首选）：resultMeta.attributes 回传查询参数**

MCP 工具把生成图表时的查询参数写入 resultMeta（已有字段，无需改 schema）：

```json
{
  "resultMeta": {
    "requestId": "...",
    "generatedAt": "...",
    "attributes": { "personId": "person-001", "startTime": "...", "endTime": "..." }
  }
}
```

前端从 `result.resultMeta.attributes` 取 personId 填占位符。**工具开发规范要求**：凡是结果粒度丢失了查询主体的工具，必须把查询参数回填到 attributes——写入开发框架文档。

**来源 B（兜底）：让 LLM 从会话上下文推断**

若模板中 `{personId}` 无法从 A 解析，前端替换为空并在追问前缀加"关于当前分析对象"。LLM 从 ChatMemory 记得上文是谁。这是自然语言的容错优势，但优先 A（确定性）。

### 4.3 下钻结果数据（点击之后的明细）

**不由前端取数**。追问发出后走完整链路：LLM → `kg_list_activity(personId, 时间范围)` → 该工具自己按城市过滤（**需要工具支持过滤参数**，见 §6）→ 新 McpResult → 新 resultRef → 新 ViewHint（Timeline/Table）→ 前端渲染。

## 5. 前端交互流程（SDK 层）

### 5.1 UiSurfacePart 增强

```
挂载时: result 加载后检查 component.props 是否含 drillDown.enabled
        ├─ 无 → 图表无点击行为（现状）
        └─ 有 → cursor: pointer + 悬停 tooltip(label)
```

### 5.2 点击处理（确定性，无 LLM 参与）

```ts
function onCategoryClick(clickedRow: Record<string, unknown>) {
    const drill = component.props.drillDown
    if (!drill?.enabled) return

    const context = {
        ...clickedRow,                          // {city: '北京', count: 18}
        ...(result.resultMeta?.attributes ?? {}), // {personId: 'person-001', ...}
    }
    const question = drill.promptTemplate.replace(/\{(\w+)\}/g,
        (_, key) => String(context[key] ?? ''))

    emit('drill-down', {question, surfaceId, dimension: drill.dimension, value: context[drill.dimension]})
}
```

### 5.3 宿主接线

`UiSurfacePart` 冒出 `drill-down` 事件；宿主（App.vue / 第三方前端）决定怎么发：

```vue
<UiSurfacePart :surface="part.surface" @drill-down="onDrillDown"/>

<script setup>
function onDrillDown({question}) {
    sendMessage(question)   // 复用现有发送逻辑，像用户手动输入一样
}
</script>
```

SDK 提供 `useConversation` 时同样暴露 `send`，一行接通。

### 5.4 视觉反馈

- 下钻发起时，可在被点击的图上叠一个轻量"正在深入分析 北京…"角标（可选，第一版可不做）
- 追问气泡可选地显示为"🔗 深入分析：北京"样式的特殊消息（区别于用户手输），提升可解释性

## 6. 后端配套改造

| 项 | 改动 | 量级 |
|---|---|---|
| **schema** | ViewHint 增加 `drillDown` 可选对象 | 小 |
| **agent-client** | `PresentationMapper` 把 drillDown 透传进 component.props；`UiComponentType` 不变 | 小 |
| **mcp-server 工具** | `kg_activity_statistics` 的 ViewHint 加 drillDown 声明；resultMeta.attributes 回填 personId/时间范围 | 小 |
| **mcp-server 工具** | `kg_list_activity` 增加 `city` 可选过滤参数（下钻的数据支撑） | 小 |
| **AgentPrompt** | 无需改——LLM 收到的追问已是自然语言 | 无 |

## 7. 数据流全景

```
① 首次查询
   用户:"统计 person-001 最近一月的活动城市"
   → kg_activity_statistics(personId, t1, t2)
   → McpResult{ data:[{city,count}], presentation.views[0].drillDown{...},
                resultMeta.attributes{personId, t1, t2} }
   → resultRef=R1 → SSE ui 事件 → 柱状图渲染（可下钻态）

② 用户点击"北京"
   前端: clickedRow={city:北京, count:18}
         + resultMeta.attributes={personId:person-001}
         → 模板替换 → "深入分析 person-001 在 北京 的活动情况，展示活动明细"
   → sendMessage（与手输完全同路）

③ 下钻执行
   LLM 理解追问 → kg_list_activity(personId=person-001, city=北京)
   → 新 McpResult → R2 → Timeline/Table 渲染 → 文字解读
```

## 8. 安全与边界

1. **模板由数据提供方声明**，非 LLM 生成——promptTemplate 在服务端代码中，不可注入
2. **占位符只做字面替换**，替换值来自数据行/attributes（服务端产出的数据），前端不拼接任意用户输入进命令语义
3. **dimension 值过 LLM 再走工具参数**——即使有恶意值，最终仍被 MCP 工具的参数校验拦住
4. 未声明 drillDown 的图完全无点击行为——能力显式声明，默认关闭
5. 追问走 ChatMemory，多级下钻自然支持（点时间线某条 → 再深入），无需专门处理

## 10. 与方案原则的对照

| 原则 | 本方案的遵守方式 |
|---|---|
| 铁律一（LLM 不搬数据） | 明细由 MCP 工具返回，前端只发自然语言追问 |
| 建议与决策分离 | 数据提供方声明"可下钻+模板"，是否/如何深入仍由 LLM 处理追问 |
| UI 受控声明 | drillDown 是 ViewHint 的声明式字段，非代码 |
| §4.3 LLM 职责 | 下钻语义理解、工具选择、图文组织全部回归 LLM |
| §58 职责边界 | ViewHint=数据提供方的表达建议（扩展为交互建议） |
