# 富可视化流式响应开发框架

> 基于《LLM + MCP 富可视化流式响应技术方案》与 ai-mcp-platform 已验证实现总结。
> 目标：为"自然语言问答 → 文字 + 图表混合流式输出"类需求提供通用开发指导。

---

## 1. 核心思想（三条铁律）

整个框架围绕三个不可破坏的原则构建，任何设计决策冲突时回到这三条：

```text
铁律一：LLM 不搬运数据
    大数据存在 ResultStore，LLM 只见摘要 + resultRef，
    UI 渲染时由前端按 resultRef 拉取原始数据。

铁律二：建议与决策分离
    数据提供方（MCP Tool）给 ViewHint 建议，
    LLM 根据当前问题决定用不用，
    前端 Renderer 决定怎么画。三层各司其职。

铁律三：UI 只能是受控声明
    LLM/工具永远不生成 HTML/JS/ECharts option/G6 config，
    只能引用白名单组件类型 + 字段映射（encoding）。
```

**为什么这样做**（踩过的坑）：
- LLM 复制数据 → token 浪费、数值幻觉、ID 丢失
- LLM 生成 ECharts 配置 → 注入风险 + 不可维护
- 工具强制绑定 UI → 同一数据无法服务不同问题（"最后一次去哪"不需要图，"活动规律分析"需要）

## 2. 端到端机制总览

```text
用户问句
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ 第一阶段：数据返回（MCP Data Tool）                        │
│                                                         │
│  Tool 在服务端完成聚合/统计（不让 LLM 算数）               │
│  返回 McpResult<T> envelope:                             │
│    data         完整业务数据                              │
│    summary      摘要+highlights（给 LLM 看的）            │
│    presentation ViewHint[]（推荐的视图，轻量建议）          │
│                                                         │
│  Agent Host 侧:                                          │
│    McpResult → ResultStore.save() → resultRef            │
│    ObservationBuilder 生成给 LLM 的文字:                  │
│      摘要 + resultRef + 推荐视图列表 + "按需使用"提示      │
└─────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ 第二阶段：渲染决策（LLM）                                  │
│                                                         │
│  LLM 读 Observation，结合当前问题判断：                    │
│    a) 文字已足够 → 直接回答（不调用 ui_render）            │
│    b) 可视化有价值 → 调用 ui_render(resultRef, viewId)    │
│                                                         │
│  PresentationRuntime 执行:                               │
│    校验 viewId 合法性 → 校验 mapping → 生成 SurfaceSpec   │
│    (surfaceId + dataRef + components[]) → 发 UI 事件     │
│  LLM 继续输出文字（图后还可以有文字）                       │
└─────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ 第三阶段：前端渲染（Vue Renderer）                         │
│                                                         │
│  SSE 流: delta(文字) / ui(SurfaceSpec) / done 交错到达    │
│                                                         │
│  消息模型 Message.parts[]: TextPart 与 UiPart 交错        │
│  UiPart:                                                │
│    1. 收到 ui 事件 → 插入 UiPart（loading 态）            │
│    2. 按 dataRef 调 GET /api/results/{ref} 拉数据         │
│    3. ComponentRegistry 按 type 路由到 Renderer           │
│    4. Renderer 解析 encoding → 渲染（ECharts/G6/Vue）     │
└─────────────────────────────────────────────────────────┘
```

## 3. 协议规范

### 3.1 MCP Data Tool 返回：McpResult envelope

```json
{
  "specVersion": "1.1",
  "success": true,
  "data": [ {"city": "北京", "count": 18} ],
  "summary": {
    "count": 3,
    "description": "按城市统计活动次数",
    "highlights": ["北京18次"]
  },
  "presentation": {
    "mode": "RECOMMENDED",
    "views": [ ViewHint ]
  }
}
```

规则：
- `success=false` 时走 `error: {code, message, retryable}`，与 MCP 协议错误分开处理
- `summary.highlights` 是服务端**确定性计算**的事实，不是 LLM 猜的
- `presentation.mode`：`NONE`/`RECOMMENDED`/`REQUIRED`，通常使用 `RECOMMENDED`
- 可选对象不适用时省略，不使用 `null` 占位；失败结果的 `data` 必须显式为 `null`

### 3.2 ViewHint：语义映射，不含绘制细节

```json
{
  "id": "city-stat",
  "type": "chart",
  "subType": "bar",
  "title": "各城市活动次数",
  "mapping": { "category": "city", "value": "count" }
}
```

mapping 表达**数据字段 → 图语义**的对应，第一版支持四类：

| type | mapping 字段 | 前端 Renderer |
|---|---|---|
| chart | category, value | ECharts (bar/line/area/pie/scatter) |
| timeline | time, title, description, group | Vue 垂直时间线 |
| relation_graph | source, target, label | AntV G6 |
| table | columns[{field,label}]（可省略自动推导） | Vue 表格 |

### 3.3 Observation（给 LLM 的工具结果文本）

```text
工具 kg_activity_statistics 执行成功。
结果摘要:
按城市统计活动次数
结果数量: 3
北京18次
resultRef: result_a12b34c
推荐展示（按需选择，不要为了展示而展示）:
viewId=city-stat, type=chart, subType=bar, title=各城市活动次数
需要展示时调用 ui_render；文字已足够时不要调用。
```

### 3.4 SSE 事件流（AG-UI 思想兼容）

| 事件 | 载荷 | 说明 |
|---|---|---|
| `delta` | `{conversationId, runId, content}` | 文字增量（TEXT_MESSAGE_CONTENT） |
| `ui` | `{conversationId, runId, surfaceId, dataRef, components[]}` | UI 创建（CUSTOM: ui.surface.create） |
| `done` | — | 本轮结束（RUN_FINISHED） |
| `error` | `{content}` | 降级提示，不暴露内部堆栈 |

关键实现细节：`ui` 事件与 `delta` 按**时间序 merge** 在同一条 SSE 流中（图出现在文字中间），`ui` 流以 RUN_FINISHED 为终止信号，`done` 事件最后补发。

### 3.5 数据端点

```text
GET /api/results/{resultRef}
→ { resultRef, serverCode, toolName, data, summary, expiresAtEpochMs }
```

UI 不复制数据，只携带 dataRef；前端渲染时才拉取。TTL 默认 45 分钟（Caffeine），过期返回 404，前端显示错误态。

## 4. 各层职责速查（出现问题时先查边界）

| 层 | 负责 | 绝不负责 |
|---|---|---|
| MCP Data Tool | 业务数据 + summary + ViewHint | 决定是否展示；怎么画 |
| ResultStore | resultRef ↔ 完整数据，TTL | — |
| ObservationBuilder | 摘要文本化 + resultRef + 视图建议 | 塞完整数据给 LLM |
| LLM | 判断是否 ui_render、文字组织、图文顺序 | 生成绘制配置；复制数据 |
| PresentationRuntime | viewId 校验、mapping 校验、SurfaceSpec 生成 | 数据计算 |
| SSE 层 | delta/ui/done 交错下发 | — |
| 前端 UiPart | dataRef 拉数、Registry 路由、loading/error 态 | 解析业务语义 |
| Renderer | encoding → 具体图形库 option | 请求网络；理解业务 |

## 5. 开发流程（新增一个可视化工能的步骤）

### 5.1 后端：新增 MCP Data Tool

1. Service 层实现业务查询，**聚合在服务端完成**（禁止返回原始大表让 LLM 统计）
2. Tool 类加 `@McpTool(name, description)`，返回 `McpResult.success(data, summary, hint, meta)`
3. 若数据适合可视化，构造对应 ViewHint 并放入 `PresentationHint.recommended(view)`
4. **不要**加 `generateOutputSchema = true`（多态 ViewHint + null 字段会导致 schema 校验误报，已踩坑）

### 5.2 前端：确认/新增 Renderer

1. 查 ComponentRegistry：ViewHint.type 是否已有 Renderer？
2. 已有 → 无需改动；没有 → 在 `presentation/` 新建 `XxxRenderer.vue`：
   - props: `{component, result}`
   - 解析 `component.props.encoding` 得到字段映射
   - 从 `result.data`（Array<Object>）取数渲染
   - 白名单校验 subType 等枚举值
   - 图形库实例要处理**容器初始宽度问题**（ResizeObserver + RAF 延迟 resize，见 7.1）
3. 注册进 UiPart 的 registry

### 5.3 验证清单

```text
□ curl 直接调 /api/chat/messages，确认 SSE 里 delta/ui/done 齐全
□ ui 事件的 dataRef 能从 /api/results/{ref} 拉到数据
□ encoding 字段名与 data 行的键完全一致
□ 浏览器：loading → 图表正常 → 图后文字继续
□ 多轮：新数据新维度会出图；简单追问不重复出图
□ 错误路径：不存在的实体 → 业务失败 → 文字提示，不崩流
```

## 6. System Prompt 模板（渲染决策的关键）

```text
你可以调用 MCP 工具获取业务数据。
MCP 工具结果中的 presentation.views 只是推荐的表达形式，不要求一定展示。
只有图表/关系图/时间线/表格能明显提升理解效率时，才调用 ui_render。
调用 ui_render 时必须使用 Observation 中的 resultRef 和推荐的 viewId；
不要复制原始数据，不要生成 ECharts、G6、HTML、JavaScript、Vue 配置。

多轮对话规则：
- 每一轮新调用 MCP 工具得到的 Observation 都有新的 resultRef。
- 本轮回答核心是新数据 → 即使之前出过图，也应为新数据调用 ui_render。
- 简单追问（单一事实）→ 文字即可，无需重复出图。
- 新的分析维度/统计/关系数据出现 → 应当出图。
```

经验参数（trs-m6 / vLLM 网关实测）：
- `extra_body.chat_template_kwargs.enable_thinking: false` 提速 100 倍（10min → 3s）
- vLLM 流式 tool_calls 碎片（name=null）需在 OpenAiApi 传输层合并，见 7.3

## 7. 已知陷阱与解法（必读）

### 7.1 图表容器初始宽度为 0/过小

**现象**：柱子极细挤在一起，或全部叠在同一 X 位置。
**根因**：`echarts.init()` 时消息气泡还在布局中，容器宽度不是最终值；`barMinWidth` 在窄画布下强制柱宽导致重叠。
**解法**：Renderer 内用 `ResizeObserver` 监听容器 + `requestAnimationFrame` 延迟 resize；只设 `barMaxWidth` 不设 `barMinWidth`。

### 7.2 SSE 流不结束（done 不发）

**现象**：curl 一直挂到超时。
**根因**：ui 事件流（事件总线）是无限流，merge 后整个流永不 complete；`takeUntil("done")` 逻辑上永远等不到（done 在 concat 之后才发）。
**解法**：ui 流用 `takeUntilOther(RUN_FINISHED 信号)` 截断，done 由 textStream 完成后 concat 补发。

### 7.3 vLLM 网关流式 tool_calls 碎片

**现象**：`ToolCall(name=null)` NPE，`DefaultToolCallingManager` 崩溃。
**根因**：vLLM 每个 chunk 都带 tool_calls（首 chunk 有 name，后续 name=null），Spring AI 逐 chunk 触发工具执行。
**解法**：自定义 `OpenAiApi` 子类，在 `chatCompletionStream(request, headers)`（**必须 override 两参版本**，内部递归也走它）里按 index 合并 chunk，finish_reason 到达时发出完整 ToolCall。

### 7.4 MCP 服务重启后 session 失效

**现象**：`Session not found` → 整轮 error。
**解法**：agent-client 的 MCP client 懒初始化缓存了旧 session；重启 agent-client 清理。（框架改进方向：McpClientManager 增加 session 失效自动重连。）

### 7.5 @PathVariable 参数名丢失

**现象**：`GET /api/results/{ref}` 500。
**根因**：编译未开 `-parameters`，Spring 拿不到参数名。
**解法**：显式写 `@PathVariable("resultRef")`，或编译参数加 `-parameters`。

### 7.6 LLM 重复调用同一工具上百次

**现象**：无 thinking 模式下工具结果校验失败，模型循环重试。
**根因**：MCP 服务端 outputSchema 校验误报（null 字段/多态 ViewHint），LLM 认为"工具坏了"反复重调。
**解法**：移除 `generateOutputSchema`；本质是保证 Observation 反馈的信息是"可理解的失败原因"，避免模型陷入重试循环。

## 8. 扩展路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| 一 | chart/timeline/relation_graph/table 四类渲染器 + parts 消息模型 + SSE ui 事件 | ✅ 已完成 |
| 二 | Metric/EntityCard 组件；UI_UPDATE 增量更新（surface.update/data.update）；图表点击下钻 | 待做 |
| 三 | MCP App Tool（ui:// resource + iframe，复杂专属 UI）；Skill 层（分析策略） | 待做 |
| 四 | AG-UI/A2UI 正式兼容（多 Agent Runtime 接入时） | 按需 |

第二阶段要点：
- `UI_UPDATE` 事件已定义未消费，前端 UiPart 需支持按 surfaceId 更新（status: loading→ready→error 之外的 data 刷新）
- 下钻 = 图表点击 → 前端发新消息（携带过滤条件）→ 复用现有链路，不需要新协议

## 10. 一页决策树（贴墙版）

```text
要返回数据给 LLM？
  └─ 能聚合吗？→ 服务端聚合，返回 McpResult(data+summary+ViewHint)
       └─ LLM 需要看的 → ObservationBuilder 摘要+resultRef
            └─ LLM 要展示吗？
                 ├─ 否 → 纯文字（不调 ui_render）
                 └─ 是 → ui_render(resultRef, viewId)
                          → SurfaceSpec(dataRef, components)
                          → SSE ui 事件
                          → 前端拉 /api/results/{dataRef}
                          → Registry 路由 → Renderer(encoding→图)
```
