# 测试问句

本文提供一组可以直接在前端输入的测试问题，用于验证 Spring AI Alibaba Runtime、MCP 工具调用、AG-UI 流式事件以及 `@ac/agent-ui` 富组件渲染效果。

当前 MCP Server 的内置模拟数据主要围绕 `person-001`，支持活动统计、活动明细、实体查询、证据查询和关系扩展。

## 1. 柱状图

输入：

> 请统计 person-001 最近 30 天在各城市的活动次数，调用知识库工具，并按推荐视图用柱状图展示。

预期效果：

- 调用 `kg_activity_statistics`；
- Assistant 文字流式输出；
- 出现“各城市活动次数”柱状图；
- 数据大致为北京 8 次、上海 5 次、杭州 3 次；
- 图表前后包含必要的引导和分析文字。

## 2. 时间线

输入：

> 查询 person-001 最近 30 天的全部活动明细，并按时间线展示。

预期效果：

- 调用 `kg_list_activity`；
- 展示活动时间线；
- 时间线包含城市、时间、活动类型和活动描述。

也可以测试城市过滤：

> 查询 person-001 最近 30 天在北京的活动明细，用时间线展示。

预期只显示北京地区的活动。

## 3. 图表点击下钻

首先输入：

> 统计 person-001 最近 30 天在各城市的活动次数，用柱状图展示。

图表出现后，点击“北京”柱子。

预期自动生成类似问题：

> 深入分析 person-001 在北京的活动情况，展示活动明细时间线。

该流程用于验证：

```text
柱状图
  → 点击数据项
  → 根据 drillDown 模板生成追问
  → 再次调用 MCP
  → 展示对应城市的活动时间线
```

## 4. 关系图

输入：

> 查询 person-001 的关系网络，扩展两层，并用关系图展示。

预期效果：

- 调用 `kg_expand_relations`；
- 展示关系网络；
- 当前模拟数据中会出现 `person-001 → person-002` 的 `KNOWS` 关系。

## 5. 普通实体查询

输入：

> 搜索名称为“张三”的实体，并介绍查询结果。

或者：

> 查询 person-001 的实体详情。

这类问题主要测试 MCP 工具调用和普通文本回答。当前实体工具没有推荐可视化视图，因此正常情况下不会出现图表。

## 6. 简单事实追问

首先生成活动柱状图：

> 统计 person-001 最近 30 天在各城市的活动次数，并用柱状图展示。

然后追问：

> 活动最多的城市是哪个？

预期只回答“北京”，不重复生成图表。这可以验证“简单事实使用文字回答”的规则。

继续追问：

> 展开北京的活动明细，并用时间线展示。

预期产生新的 MCP Result 和新的时间线，而不是复用上一轮的 ResultReference。

## 7. 多工具组合

输入：

> 先统计 person-001 最近 30 天各城市的活动次数，再查询活动最多城市的明细，并分别用柱状图和时间线展示。

该问题用于测试：

- 连续调用多个 MCP 工具；
- 一次运行中保存多个 ResultReference；
- 一条回答中插入多个 Rich UI Surface；
- 文本、柱状图和时间线交错展示；
- 多次 `ui_render` 调用与 Surface 事件顺序。

## 8. 无数据和安全降级

输入：

> 查询 person-999 最近 30 天的活动，并展示结果。

预期效果：

- 工具调用正常完成；
- 返回空数据或“没有活动”的文字提示；
- 前端不会因为空数据报错；
- 不应展示包含虚构数据的图表。

## 9. 纯文本基线

输入：

> 你好，请介绍一下你能做什么。

预期效果：

- 不调用 MCP 工具；
- 不生成 Rich UI；
- 只返回普通流式文本；
- 正常产生唯一的运行终态事件。

## 10. 推荐完整测试顺序

建议按照以下顺序测试：

1. 输入“你好，请介绍一下你能做什么。”，验证纯文本流式响应。
2. 输入“统计 person-001 最近 30 天各城市的活动次数，并用柱状图展示。”，验证统计工具和柱状图。
3. 点击柱状图中的“北京”，验证点击下钻和时间线。
4. 输入“活动最多的城市是哪个？”，验证简单追问不会重复出图。
5. 输入“查询 person-001 的关系网络，扩展两层，并用关系图展示。”，验证关系图。
6. 输入“查询 person-999 最近 30 天的活动。”，验证空数据降级。
7. 输入多工具组合问题，验证多个 MCP Tool 和 Rich UI Surface 的事件顺序。

## 11. 模型未触发 Rich UI 时

是否调用 `ui_render` 最终由模型结合系统提示和工具结果决定。如果模型只返回文字，可以使用更明确的问题：

> 请务必调用知识库 MCP 工具获取真实数据，并使用工具结果中推荐的 viewId 调用 ui_render 展示，不要自行编造数据。

也可以将具体任务写入同一个问题：

> 请务必调用知识库 MCP 工具，统计 person-001 最近 30 天在各城市的活动次数，并使用工具结果中推荐的 resultRef 和 viewId 调用 ui_render 展示柱状图。

不要在问题中要求模型直接生成 ECharts、G6、HTML、JavaScript 或 Vue 配置。Rich UI 应由 MCP Result 中的 PresentationHint 和前端 Renderer 完成。

## 12. 当前可视化覆盖情况

| Renderer | 当前测试入口 | 推荐问句 |
| --- | --- | --- |
| Chart | `kg_activity_statistics` | 统计 `person-001` 最近 30 天各城市的活动次数 |
| Timeline | `kg_list_activity` | 查询 `person-001` 最近 30 天的活动明细 |
| RelationGraph | `kg_expand_relations` | 查询 `person-001` 的关系网络并扩展两层 |
| Table | 暂无稳定的推荐视图入口 | 当前 MCP 工具尚未提供表格类型的 PresentationHint |

SDK 已内置 Table Renderer，但当前 MCP Server 工具尚未返回推荐的表格视图，因此暂时没有稳定触发表格的自然语言测试问题。

## 13. 观察重点

测试过程中建议同时观察以下行为：

- Assistant 文本是否逐段流式显示；
- 工具调用是否具有稳定的 `toolCallId`；
- Rich UI 到达后是否先显示骨架屏，再替换为真实组件；
- 图表数据是否通过 ResultReference 从结果接口读取；
- 图表是否出现在对应文字段落之间，而不是统一堆积在消息末尾；
- 一次运行是否只产生一个 `RUN_FINISHED` 或 `RUN_ERROR` 终态；
- 切换 thread 或同时发起多个 run 时，事件和结果是否相互隔离；
- 空数据、结果过期或组件加载失败时，文字流是否仍能正常完成。

## 14. 同一会话连续三轮回归

在同一个浏览器会话和同一个 `threadId` 中，依次发送以下三个问句。每轮使用新的 `runId`，等待上一轮结束后再发送下一轮。

1. `请统计 person-001 最近 30 天在各城市的活动次数`
2. `活动最多的城市是哪个？`
3. `展开北京的活动明细`

预期事件：

| 轮次 | 工具与界面 | 终态 |
| --- | --- | --- |
| 1 | `kg_activity_statistics`；同一 `resultRef + city-stat` 最多一个柱状图 | 一个 `RUN_FINISHED` |
| 2 | 直接回答“北京”；不重复出图 | 一个 `RUN_FINISHED` |
| 3 | `kg_list_activity`；同一 `resultRef + activity-timeline` 最多一个时间线 | 一个 `RUN_FINISHED` |

如果模型或工具执行超出 `ac.ag-ui.run-timeout`（默认 2 分钟），服务端应发送一个 `RUN_ERROR` 并关闭本轮 SSE，前端不应一直保持“智能体执行中”。统计工具的时间参数应使用带时区的 ISO-8601 Instant，例如 `2026-09-01T00:00:00Z`。

## 15. 第二阶段新增视图问句（实施后执行）

本节对应《[富可视化流式响应第二阶段实施设计](富可视化流式响应第二阶段实施设计.md)》第 8、10 节。以下工具、`McpResult 1.2`、`ac.rich-ui/1.1` 和六种 Renderer 尚属第二阶段实施范围；应在启用 `demo`/`test` 演示工具后运行。这里的“可视化”包括指标卡、实体卡、树、热力图、路径和证据链，不都要求绘制统计图。输入部分使用普通用户会提出的问题；工具调用和 `ui_render` 属于预期执行路径，由测试时观察确认。

### 15.1 指标卡 Metric

输入：

> person-001 的活动概况怎么样？请用指标卡展示活动总数和涉及的城市数。

预期调用 `kg_activity_metrics(personId="person-001")`，以 `activity-metrics` 出图；页面出现“活动概览”指标卡，显示“活动总数 16 次”和“涉及城市 3 个”。

### 15.2 实体卡 EntityCard

输入：

> 有哪些与 person 相关的实体？请用卡片列出它们的名称和简介。

预期调用 `kg_entity_cards(keyword="person")`，以 `entity-cards` 展示两张卡：`person-001/张三` 与 `person-002/李四`。这与第 5 节的当前普通实体查询不同，专门验收第二阶段的实体卡工具。

### 15.3 树 Tree

输入：

> org-root 的基础组织结构是什么样的？请先用树形图展示目前查到的层级。

预期调用 `kg_relation_tree(rootId="org-root", snapshot="base")`，以 `org-tree` 先显示“示例机构”；点击后在本地展开“研发部”。此时“研发部”尚无已加载子节点，应显示“查看子节点详情”，点击后按 `drillDown` 模板发起新对话，不把未加载的“数据组”直接画出来。

### 15.4 热力图 Heatmap

输入：

> person-001 在各个城市分别有哪些类型的活动？请用热力图展示分布。

预期调用 `kg_activity_heatmap(personId="person-001")`，以 `activity-heatmap` 展示 9 个有数据的格子，计数合计 16；北京 `BUSINESS=4`、上海 `BUSINESS=3`，未出现的城市/类型组合标为“无数据”，不显示为 0。

### 15.5 关系路径 RelationshipPath

输入：

> person-001 和 org-root 之间是怎么关联起来的？请把关联路径展示出来。

预期调用 `kg_relationship_path(sourceId="person-001", targetId="org-root")`，以 `person-org-path` 展示两步：`person-001 → person-002`（`KNOWS`），再到 `org-root`（`WORKS_AT`）。

### 15.6 证据链 EvidenceChain

输入：

> 有哪些与 person-001 相关的证据？请按顺序展示证据链和来源。

预期调用 `kg_evidence_chain(entityId="person-001")`，以 `person-evidence` 展示 `ev-001`“登记记录”和 `ev-002`“活动记录”及其来源。`evidenceRef` 仅作为标识显示，不作为可访问链接。

### 15.7 同一次运行更新树数据

输入：

> 请先用树形图展示 org-root 的基础组织结构，再补充显示到数据组，并在同一张树上更新。

预期事件顺序为 `ui.surface.create` → `ui.surface.update`，`surfaceId` 不变、`dataRef` 改为新结果；最终树显示“示例机构 → 研发部 → 数据组”，同时仍保留文字回答。两次 MCP 查询本身不会自动触发更新。自然语言模型可能无法稳定执行这一串工具调用，最终以同一 run 的集成测试作为协议验收依据。
