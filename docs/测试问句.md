# 测试问句

本文提供一组可以直接在前端输入的测试问题，用于验证 Spring AI Alibaba Runtime、MCP 工具调用、AG-UI 流式事件以及 `@ac/agent-ui` 富组件渲染效果。

当前 MCP Server 的内置模拟数据主要围绕 `person-001`，支持活动统计、活动明细、实体查询、证据查询和关系扩展。

第三阶段新增资金流分析演示，业务问句见第 16 节。资金数据为独立的确定性样例，不代表 `person-001` 的真实银行账户或交易。

## 1. 柱状图

输入：

> 请统计 person-001 最近 30 天在各城市的活动次数，调用知识库工具，并按推荐视图用柱状图展示。

预期效果：

- 调用 `kg_activity_statistics`；
- Assistant 文字流式输出；
- 出现“各城市活动次数”柱状图；
- 数据大致为北京 8 次、上海 5 次、杭州 3 次；
- 图表前后包含必要的引导和分析文字。

## 2. 时间线

输入：

> 查询 person-001 最近 30 天的全部活动明细，并按时间线展示。

预期效果：

- 调用 `kg_list_activity`；
- 展示活动时间线；
- 时间线包含城市、时间、活动类型和活动描述。

也可以测试城市过滤：

> 查询 person-001 最近 30 天在北京的活动明细，用时间线展示。

预期只显示北京地区的活动。

## 3. 图表点击下钻

首先输入：

> 统计 person-001 最近 30 天在各城市的活动次数，用柱状图展示。

图表出现后，点击“北京”柱子。

预期自动生成类似问题：

> 深入分析 person-001 在北京的活动情况，展示活动明细时间线。

该流程用于验证：

```text
柱状图
  → 点击数据项
  → 根据 drillDown 模板生成追问
  → 再次调用 MCP
  → 展示对应城市的活动时间线
```

## 4. 关系图

输入：

> 查询 person-001 的关系网络，扩展两层，并用关系图展示。

预期效果：

- 调用 `kg_expand_relations`；
- 展示关系网络；
- 当前模拟数据中会出现 `person-001 → person-002` 的 `KNOWS` 关系。

## 5. 普通实体查询

输入：

> 搜索名称为“张三”的实体，并介绍查询结果。

或者：

> 查询 person-001 的实体详情。

这类问题主要测试 MCP 工具调用和普通文本回答。当前实体工具没有推荐可视化视图，因此正常情况下不会出现图表。

## 6. 简单事实追问

首先生成活动柱状图：

> 统计 person-001 最近 30 天在各城市的活动次数，并用柱状图展示。

然后追问：

> 活动最多的城市是哪个？

预期只回答“北京”，不重复生成图表。这可以验证“简单事实使用文字回答”的规则。

继续追问：

> 展开北京的活动明细，并用时间线展示。

预期产生新的 MCP Result 和新的时间线，而不是复用上一轮的 ResultReference。

## 7. 多工具组合

输入：

> 先统计 person-001 最近 30 天各城市的活动次数，再查询活动最多城市的明细，并分别用柱状图和时间线展示。

该问题用于测试：

- 连续调用多个 MCP 工具；
- 一次运行中保存多个 ResultReference；
- 一条回答中插入多个 Rich UI Surface；
- 文本、柱状图和时间线交错展示；
- 多次 `ui_render` 调用与 Surface 事件顺序。

## 8. 无数据和安全降级

输入：

> 查询 person-999 最近 30 天的活动，并展示结果。

预期效果：

- 工具调用正常完成；
- 返回空数据或“没有活动”的文字提示；
- 前端不会因为空数据报错；
- 不应展示包含虚构数据的图表。

## 9. 纯文本基线

输入：

> 你好，请介绍一下你能做什么。

预期效果：

- 不调用 MCP 工具；
- 不生成 Rich UI；
- 只返回普通流式文本；
- 正常产生唯一的运行终态事件。

## 10. 推荐完整测试顺序

建议按照以下顺序测试：

1. 输入“你好，请介绍一下你能做什么。”，验证纯文本流式响应。
2. 输入“统计 person-001 最近 30 天各城市的活动次数，并用柱状图展示。”，验证统计工具和柱状图。
3. 点击柱状图中的“北京”，验证点击下钻和时间线。
4. 输入“活动最多的城市是哪个？”，验证简单追问不会重复出图。
5. 输入“查询 person-001 的关系网络，扩展两层，并用关系图展示。”，验证关系图。
6. 输入“查询 person-999 最近 30 天的活动。”，验证空数据降级。
7. 输入多工具组合问题，验证多个 MCP Tool 和 Rich UI Surface 的事件顺序。

## 11. 模型未触发 Rich UI 时

是否调用 `ui_render` 最终由模型结合系统提示和工具结果决定。如果模型只返回文字，可以使用更明确的问题：

> 请务必调用知识库 MCP 工具获取真实数据，并使用工具结果中推荐的 viewId 调用 ui_render 展示，不要自行编造数据。

也可以将具体任务写入同一个问题：

> 请务必调用知识库 MCP 工具，统计 person-001 最近 30 天在各城市的活动次数，并使用工具结果中推荐的 resultRef 和 viewId 调用 ui_render 展示柱状图。

不要在问题中要求模型直接生成 ECharts、G6、HTML、JavaScript 或 Vue 配置。Rich UI 应由 MCP Result 中的 PresentationHint 和前端 Renderer 完成。

## 12. 当前可视化覆盖情况

| Renderer | 当前测试入口 | 推荐问句 |
| --- | --- | --- |
| Chart | `kg_activity_statistics` | 统计 `person-001` 最近 30 天各城市的活动次数 |
| Timeline | `kg_list_activity` | 查询 `person-001` 最近 30 天的活动明细 |
| RelationGraph | `kg_expand_relations` | 查询 `person-001` 的关系网络并扩展两层 |
| Table | 暂无稳定的推荐视图入口 | 当前 MCP 工具尚未提供表格类型的 PresentationHint |

SDK 已内置 Table Renderer，但当前 MCP Server 工具尚未返回推荐的表格视图，因此暂时没有稳定触发表格的自然语言测试问题。

## 13. 观察重点

测试过程中建议同时观察以下行为：

- Assistant 文本是否逐段流式显示；
- 工具调用是否具有稳定的 `toolCallId`；
- Rich UI 到达后是否先显示骨架屏，再替换为真实组件；
- 图表数据是否通过 ResultReference 从结果接口读取；
- 图表是否出现在对应文字段落之间，而不是统一堆积在消息末尾；
- 一次运行是否只产生一个 `RUN_FINISHED` 或 `RUN_ERROR` 终态；
- 切换 thread 或同时发起多个 run 时，事件和结果是否相互隔离；
- 空数据、结果过期或组件加载失败时，文字流是否仍能正常完成。

## 14. 同一会话连续三轮回归

在同一个浏览器会话和同一个 `threadId` 中，依次发送以下三个问句。每轮使用新的 `runId`，等待上一轮结束后再发送下一轮。

1. `请统计 person-001 最近 30 天在各城市的活动次数`
2. `活动最多的城市是哪个？`
3. `展开北京的活动明细`

预期事件：

| 轮次 | 工具与界面 | 终态 |
| --- | --- | --- |
| 1 | `kg_activity_statistics`；同一 `resultRef + city-stat` 最多一个柱状图 | 一个 `RUN_FINISHED` |
| 2 | 直接回答“北京”；不重复出图 | 一个 `RUN_FINISHED` |
| 3 | `kg_list_activity`；同一 `resultRef + activity-timeline` 最多一个时间线 | 一个 `RUN_FINISHED` |

如果模型或工具执行超出 `ac.ag-ui.run-timeout`（默认 2 分钟），服务端应发送一个 `RUN_ERROR` 并关闭本轮 SSE，前端不应一直保持“智能体执行中”。统计工具的时间参数应使用带时区的 ISO-8601 Instant，例如 `2026-09-01T00:00:00Z`。

## 15. 第二阶段新增视图问句

本节对应《[富可视化流式响应第二阶段实施设计](富可视化流式响应第二阶段实施设计.md)》第 8、10 节。当前 MCP Server 默认注册本节使用的演示工具，无需添加 `--spring.profiles.active=demo` 等启动参数。这里的“可视化”包括指标卡、实体卡、树、热力图、路径和证据链，不都要求绘制统计图。输入部分使用普通用户会提出的问题；工具调用和 `ui_render` 属于预期执行路径，由测试时观察确认。

### 15.1 指标卡 Metric（知识库概览）

输入：

> 演示知识库里有多少个人员实体、组织节点和证据记录？请用指标卡展示这三个总数。

预期调用无参数工具 `kg_knowledge_overview()`，然后使用本轮返回的 `resultRef` 和 `viewId="knowledge-overview"` 调用 `ui_render`；推荐视图为 `type="metric"`、`subType="single"`，页面出现“演示知识库概览”三张指标卡：人员实体 2 个、组织节点 3 个、证据记录 2 条。数量来自演示 fixture，组织节点包含完整展开后的“示例机构、研发部、数据组”。

如果模型没有选中该工具，可以用以下明确指定工具的问句排查：

> 请调用 kg_knowledge_overview 查询演示知识库的数据概览，再使用它返回的 resultRef 和 knowledge-overview 视图调用 ui_render，以指标卡展示人员实体、组织节点和证据记录总数。

前提：更新代码后先重启 MCP Server，再重启 Agent Client，确认工具列表包含 `kg_knowledge_overview`。MCP Server 默认加载全部工具，不需要指定 profile。Agent Client 的 `AgentFactory` 会缓存已构建的 Agent 及其工具列表，仅重启 MCP Server 或新建前端会话不会刷新该缓存。建议新建会话测试。

若长时间等待后出现 `RUN_ERROR/code="TimeoutException"`，表示本轮执行超时，不能仅凭这条终态判断指标卡渲染失败。当前整轮上限为 `ac.ag-ui.run-timeout`（默认 2 分钟），MCP 请求超时单独由 `ac.mcp.servers[].timeout` 控制（当前知识库配置为 30 秒）。排查时保留完整 SSE，至少核对：

- `TOOL_CALL_START` 是否选择 `kg_knowledge_overview`；
- 对应 `TOOL_CALL_END`、`TOOL_CALL_RESULT` 是否到达，结果是否含 `resultRef`；
- 是否继续调用 `ui_render`，其 `viewId` 是否为 `knowledge-overview`；
- 是否出现 `CUSTOM/name="ui.surface.create"` 且组件类型为 `Metric`。已收到该事件后再超时，应继续排查后续模型响应。

服务端会按 `threadId/runId` 记录运行失败代码和整轮超时配置。缺少工具结束事件时应排查工具执行；工具已结束而下一步长时间无事件时，应结合 Agent Client 日志排查模型请求。不要仅通过延长整轮超时来判断问题已解决。

若前端显示 `The UI surface does not match the ac.rich-ui schema`，检查真实 Surface 的 `encoding`。可选字段未设置时必须省略，例如 Metric 未映射变化量时不应出现 `"change": null`。当前服务端已统一省略未设置的映射字段；更新后需要重启 Agent Client。在线回归现已将真实 SSE 送入前端 reducer 校验，不能只凭组件类型为 `Metric` 判定展示成功。

模型配置中的 `chat_template_kwargs.enable_thinking=false` 应出现在实际模型请求中。当前兼容客户端会在发送前补回 Spring AI 合并工具定义时丢失的 `extra_body` 默认项，同时保留请求显式设置的值。指标卡创建后仍超时时，应核对这一参数是否传递，以及后续模型响应是否结束。

原问句“person-001 的活动概况怎么样？请用指标卡展示活动总数和涉及的城市数。”仍可用于 `kg_activity_metrics(personId="person-001")` 回归，预期为 `activity-metrics` 的两张指标卡（活动总数 16 次、涉及城市 3 个）。如果出现柱状图，检查调用记录：`kg_activity_statistics` 返回的是 `city-stat/chart/bar`，渲染链路按工具推荐视图展示，不会仅凭问句把柱状图改成指标卡。`kg_activity_metrics` 已默认注册；旧进程未加载更新或模型选错工具时，不能据此判断 Metric Renderer 失效。

### 15.2 实体卡 EntityCard

输入：

> 有哪些与 person 相关的实体？请用卡片列出它们的名称和简介。

预期调用 `kg_entity_cards(keyword="person")`，以 `entity-cards` 展示两张卡：`person-001/张三` 与 `person-002/李四`。这与第 5 节的当前普通实体查询不同，专门验收第二阶段的实体卡工具。

### 15.3 树 Tree

输入：

> org-root 的基础组织结构是什么样的？请先用树形图展示目前查到的层级。

预期调用 `kg_relation_tree(rootId="org-root", snapshot="base")`，以 `org-tree` 先显示“示例机构”；点击后在本地展开“研发部”。此时“研发部”尚无已加载子节点，应显示“查看子节点详情”，点击后按 `drillDown` 模板发起新对话，不把未加载的“数据组”直接画出来。

### 15.4 热力图 Heatmap

输入：

> person-001 在各个城市分别有哪些类型的活动？请用热力图展示分布。

预期调用 `kg_activity_heatmap(personId="person-001")`，以 `activity-heatmap` 展示 9 个有数据的格子，计数合计 16；北京 `BUSINESS=4`、上海 `BUSINESS=3`，未出现的城市/类型组合标为“无数据”，不显示为 0。

### 15.5 关系路径 RelationshipPath

输入：

> person-001 和 org-root 之间是怎么关联起来的？请把关联路径展示出来。

预期调用 `kg_relationship_path(sourceId="person-001", targetId="org-root")`，以 `person-org-path` 展示两步：`person-001 → person-002`（`KNOWS`），再到 `org-root`（`WORKS_AT`）。

### 15.6 证据链 EvidenceChain

输入：

> 有哪些与 person-001 相关的证据？请按顺序展示证据链和来源。

预期调用 `kg_evidence_chain(entityId="person-001")`，以 `person-evidence` 展示 `ev-001`“登记记录”和 `ev-002`“活动记录”及其来源。`evidenceRef` 仅作为标识显示，不作为可访问链接。

### 15.7 同一次运行更新树数据

输入：

> 请先用树形图展示 org-root 的基础组织结构，再补充显示到数据组，并在同一张树上更新。

预期事件顺序为 `ui.surface.create` → `ui.surface.update`，`surfaceId` 不变、`dataRef` 改为新结果；最终树显示“示例机构 → 研发部 → 数据组”，同时仍保留文字回答。两次 MCP 查询本身不会自动触发更新。自然语言模型可能无法稳定执行这一串工具调用，最终以同一 run 的集成测试作为协议验收依据。

## 16. 第三阶段资金流业务问句

本节使用业务人员的表达测试资金流分析。当前演示可使用 `person-001` 作为实体标识，样例交易集中在 **2026 年 9 月 2 日至 7 日**；不要使用“最近 30 天”测试这批固定数据。以下问句中的时间均按北京时间解释。

首次展示预计使用 `kg_fund_flow_graph` 返回的专属资金流界面，界面由 MCP Server 提供，无需模型再调用 `ui_render`。运行前需构建 App 并启动独立沙箱，详见 [MCP Apps 第三阶段开发与验证](MCP-Apps第三阶段开发与验证.md)。以下为待执行的业务用例，不代表真实模型场景均已验收。

### 16.1 月度资金往来总览

输入：

> 请查看 person-001 在 2026 年 9 月的资金往来，用交互式界面展示账户之间的转账关系和交易明细，并简要介绍这批数据。

预期效果：

- 出现资金流分析界面，初始显示账户 A、账户 B；
- 交易明细包含 6 笔演示交易，金额和币种分别展示；
- 文字说明明确数据为演示数据，不将账户节点直接认定为该人员真实持有的账户；
- 可继续在界面中选中账户、展开关系和筛选交易。

### 16.2 指定几天的资金往来

输入：

> 我想重点查看 person-001 在 2026 年 9 月 2 日至 4 日这三天的资金往来，请展示交易关系和每笔转账的时间、金额、币种。

预期返回这三天的 3 笔演示交易：`12000.00 CNY`、`3800.50 CNY`、`950.00 USD`。时间范围应覆盖 9 月 4 日全天，不遗漏当天交易。

### 16.3 查看单日交易

输入：

> person-001 在 2026 年 9 月 5 日有哪些资金往来？请展示这一天的交易明细。

预期只出现该日的 `2400.00 CNY` 演示交易，不混入其他日期。该问句适合核对自然语言日期的理解。

### 16.4 展开账户往来对象

首先输入：

> 请展示 person-001 在 2026 年 9 月的资金往来，我想进一步查看某个账户与哪些账户发生过转账。

界面出现后，选择“账户 A”，点击“展开账户”。

预期图中补充显示“账户 C”，交易明细仍保留当前时间范围。展开动作直接更新业务界面，不额外生成一条分析回答。

### 16.5 关注金额较大的交易

首先输入：

> 请展示 person-001 在 2026 年 9 月的资金往来，我想在界面中筛选金额较大的交易并查看相关账户。

界面出现后，将“最低金额”设为 `3000`，点击“查询”。

预期保留 `12000.00 CNY` 和 `3800.50 CNY` 两笔交易；随后展开账户，筛选条件仍有效。当前演示按每笔交易的原币数值筛选，不能将“最低金额 3000”解释成已统一折算为人民币的门槛。

### 16.6 查看某个账户的全部交易明细

首先输入：

> 请展示 person-001 在 2026 年 9 月的账户资金往来，我想逐笔核对某个账户的收款和付款记录。

界面出现后选择“账户 A”，点击“分页查询明细”，继续点击“加载更多”。

预期展示与账户 A 相关的 4 笔演示交易，每页最多 2 笔，包含来源账户、去向账户、金额、币种和时间。切换到其他账户后应从该账户的第一页重新查看。

### 16.7 分析所选账户的收付特点

首先输入：

> 请展示 person-001 在 2026 年 9 月的资金流，我想选择一个账户，进一步分析它的收款和付款特点。

界面出现后选择“账户 A”，点击“继续分析”。当前按钮会发送：

> 分析所选账户 A 的资金往来特点。

预期新的分析回答结合所选账户的授权交易片段，区分流入、流出和币种，不把账户 A 的交易与所有账户的交易混为一谈，也不把交易片段当作完整业务统计。

### 16.8 多币种资金解释

完成第 16.7 节的账户分析后，继续输入：

### 16.9 核对值得进一步关注的交易

### 16.11 没有交易的时间段

### 16.12 结合人员活动与资金往来查看

输入：

> 请分别展示 person-001 在 2026 年 9 月的活动明细和资金往来，方便我并排查看。若数据没有提供对应关系，请不要把某次活动和某笔转账直接关联起来。

预期分别调用活动明细和资金流查询，展示活动时间线及资金流界面。当前两类数据是独立演示样例，没有账户归属和事件关联依据，不能仅凭相近日期认定资金用途或因果关系。

### 16.13 建议业务测试顺序

1. 月度总览：查看账户关系和交易明细。
2. 在同一界面展开账户、筛选金额、分页核对交易。
3. 选中账户并点击“继续分析”，再追问多币种解释及待核查事项。
4. 新建会话测试单日、两段时间对照和没有交易的时间段。
5. 测试活动与资金两类结果同时展示，检查分析是否保持事实边界。

第 16.8、16.9 节依赖上一轮账户分析的会话上下文；普通聊天追问不会自动重新提交 App 当前选择。如果在界面修改了账户或筛选条件，应再次点击“继续分析”，让后续回答使用更新后的授权数据。
