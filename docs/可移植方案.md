# 富可视化能力可移植方案

> 本文基于当前工程代码、`mcp-contract/src/main/resources/schema/mcp-result.schema.json`、Spring AI Alibaba、AG-UI 协议和 AgentScope 集成能力进行分析。
> 外部框架能力以 2026 年 9 月公开文档为准。

## 1. 结论

当前工程实现了一套设计合理的“富结果引用 + 受控声明式可视化”机制，但尚不是正式兼容 AG-UI 的实现。更准确的定位是：

> 自定义 MCP 富结果协议 + 自定义声明式 UI + AG-UI 风格的 SSE 事件流。

本工程的目标运行时应定位为 **Spring AI Alibaba Agent Framework**。需要特别区分“当前代码事实”和“目标架构”：

- 当前 `agent-client` 使用 Spring AI `ChatClient` 和手写的工具/事件编排，还没有使用 Spring AI Alibaba `ReactAgent` 或 Graph Runtime。
- 目标状态是保留 `agent-client` 作为 Agent Host 和 UI Gateway，但将其 Agent 执行核心替换为 Spring AI Alibaba Agent Framework。
- `McpResult`、`ResultStore`、Observation 摘要压缩、`PresentationRuntime`、`SurfaceSpec` 和前端 Renderer 继续作为 `agent-client` 的富结果扩展。
- 当前自定义 SSE 应演进为标准 AG-UI Adapter；截至本文编写时间，Spring AI Alibaba 尚无开箱即用的正式 AG-UI Server，因此这一适配层仍属于本工程职责。
- AgentScope v2 Java 的可移植性通过一个全新的同级应用 `agentscope-client` 验证；它只依赖 AgentScope v2 Java、公共 Rich UI 模块和必要的 Web/AG-UI 模块，不依赖 `spring-ai-alibaba-starter-agentscope`，也不依赖任何 Spring AI Alibaba Runtime 包。

最终应形成：**Spring AI Alibaba Agent Runtime + Rich Result Presentation 扩展 + 标准 AG-UI Gateway + Vue Renderer SDK**。

### 1.1 项目硬性目标

后续设计和验收以以下三项为硬性要求：

1. `agent-client` 对外提供正式兼容 AG-UI 的接口和事件流，不再把“AG-UI 风格”作为完成标准。
2. `agent-client` 的主 Agent Runtime 使用 Spring AI Alibaba Agent Framework/Graph Runtime，不再由 Spring AI `ChatClient` 手工承担 Agent Loop。
3. 富结果和富 UI 能力抽成运行时无关的公共代码，并新增独立的 `agentscope-client`（AgentScope v2 Java）进行验证；同一份 `McpResult`、ResultStore、Observation 和 Presentation 逻辑可以在两个 Runtime 中复用。

如果某项实现只能服务 Spring AI Alibaba，必须放在 SAA Adapter；如果某项实现只能服务 AgentScope，必须放在 AgentScope Adapter。公共模块禁止引用这两个框架的类型。

## 2. 当前工程机制

当前代码的完整调用链如下：

```text
Agent 调用 MCP Tool
    ↓
MCP 返回 McpResult(data + summary + presentation)
    ↓
Agent Host 保存完整 data → ResultStore → resultRef
    ↓
ObservationBuilder 只向 LLM 返回摘要、highlights、resultRef、ViewHint
    ↓
LLM 判断是否调用 ui_render(resultRef, viewId)
    ↓
PresentationRuntime 校验并生成 SurfaceSpec
    ↓
SSE 发送 UI 事件
    ↓
前端插入 UiPart，并按 resultRef 获取完整数据
    ↓
Renderer Registry 选择 Chart/Table/Timeline/RelationGraph Renderer
```

主要代码位置：

- MCP 结果解析和保存：`agent-client/.../mcp/tool/DynamicMcpToolCallback.java`
- 完整结果存储：`agent-client/.../mcp/result/InMemoryResultStore.java`
- LLM Observation 压缩：`agent-client/.../mcp/observation/DefaultObservationBuilder.java`
- Agent 展示决策工具：`agent-client/.../presentation/tool/UiRenderTool.java`
- ViewHint 校验和 Surface 生成：`agent-client/.../presentation/runtime/PresentationRuntime.java`
- 浏览器结构化流：`agent-client/.../web/ChatController.java`
- 前端数据延迟加载：`packages/agent-ui/src/components/UiSurfacePart.vue`
- 前端渲染器注册：`packages/agent-ui/src/core/registry.ts`

### 2.1 值得保留的设计原则

#### LLM 不搬运完整数据

完整数据留在 `ResultStore`，模型只看到摘要和 `resultRef`。这可以减少上下文消耗、避免模型在复制数据时丢字段或产生数值幻觉。

#### 展示建议和展示决策分离

MCP Tool 的 `PresentationHint` 只表示“这批数据适合怎样展示”，是否真的展示由 Agent 结合当前问题决定。同一批数据既能服务简单事实问答，也能服务图表分析。

#### UI 是受控声明，不是任意代码

模型和 MCP Tool 只能给出组件类型、字段映射和受控选项，不能返回 HTML、JavaScript、Vue 代码、ECharts option 或 G6 配置。最终绘制逻辑由前端受信任 Renderer 实现。

#### 数据与 UI 事件分离

UI 事件只携带 `dataRef` 和轻量 `SurfaceSpec`，前端按需获取完整数据。这样可以让文本流不被大结果阻塞。

### 2.2 当前 Agent 实现与目标实现

当前 `agent-client/pom.xml` 只引入了：

```text
org.springframework.ai:spring-ai-starter-model-openai
Spring AI 1.1.8
```

`AgentFactory` 创建的是 Spring AI `ChatClient`，通过 `defaultToolCallbacks` 装配 MCP Tool 和 `ui_render`；`AgentService` 再直接调用 `client.prompt().stream().content()`。这属于基于 Spring AI 原子能力组装的聊天代理，不等同于 Spring AI Alibaba Agent Framework。

目标实现应使用 Spring AI Alibaba 的：

```text
spring-ai-alibaba-agent-framework
ReactAgent
Graph Runtime
ToolInterceptor / AgentHook / ModelHook
Checkpointer / State
Multi-Agent Flow（按需要）
```

Spring AI Alibaba 的 `ReactAgent` 运行在 Graph Runtime 上，适合承担工具循环、状态、工作流、多 Agent 和 HITL。富结果能力应通过 ToolInterceptor、工具包装器和运行事件适配器嵌入，而不是继续在 `ChatClient` 外手写一套 Agent 循环。

依赖版本必须通过 Spring AI Alibaba BOM 对齐。不能直接把当前 Spring AI `1.1.8` 与基于其他 Spring AI 小版本发布的 Spring AI Alibaba Agent Framework 混用。具体版本以实施时的官方兼容矩阵和 Release Notes 为准。

参考：

- [Spring AI Alibaba 概览](https://java2ai.com/docs/overview/)
- [Spring AI Alibaba ReactAgent 快速开始](https://java2ai.com/docs/quick-start/)
- [Spring AI Alibaba 版本兼容表](https://java2ai.com/docs/versions/)

## 3. 与 AG-UI 的符合度

当前实现只能称为“AG-UI 思想兼容”，不能直接接入标准 AG-UI Client。

| AG-UI 维度 | 当前实现 | 判断 |
|---|---|---|
| 流式传输 | 使用 SSE | 符合传输思想 |
| 请求模型 | `{conversationId, message}` | 不符合 `RunAgentInput` |
| Run 生命周期 | 自定义 `done`，浏览器流没有标准 `RUN_STARTED` | 不符合 |
| 文本事件 | 对外发送 `delta`，没有完整 START/CONTENT/END | 不符合 |
| Tool 事件 | 自定义 `tool_start/tool_end` | 部分相似 |
| Tool 参数和结果 | 没有独立 `TOOL_CALL_ARGS`、`TOOL_CALL_RESULT` | 不符合 |
| UI 事件 | 自定义 SSE `event: ui` | 应映射为 AG-UI `CUSTOM` |
| State | 没有 `STATE_SNAPSHOT/STATE_DELTA` | 未实现 |
| 前端工具与 HITL | 未实现 | 未实现 |
| 多 Agent 事件 | 没有标准父子运行语义 | 未实现 |

AG-UI 标准请求使用 `RunAgentInput`，主要包含：

```text
threadId
runId
parentRunId
state
messages
tools
context
forwardedProps
```

标准文本事件为：

```text
TEXT_MESSAGE_START
TEXT_MESSAGE_CONTENT
TEXT_MESSAGE_END
```

标准工具事件至少包括：

```text
TOOL_CALL_START
TOOL_CALL_ARGS
TOOL_CALL_END
TOOL_CALL_RESULT
```

参考：

- [AG-UI Core Types](https://docs.ag-ui.com/sdk/js/core/types)
- [AG-UI Events](https://docs.ag-ui.com/sdk/python/core/events)
- [AG-UI Core Architecture](https://docs.ag-ui.com/concepts/architecture)

### 3.1 SurfaceSpec 与 AG-UI 的关系

`SurfaceSpec` 不必成为 AG-UI 标准事件类型。AG-UI 负责 Agent 与用户界面的运行时通信，不负责定义某一种声明式 UI Schema。A2UI、MCP-UI、Open-JSON-UI 等才属于生成式 UI 规范。

当前 `SurfaceSpec` 可以作为项目自己的 AG-UI 扩展，通过标准 `CUSTOM` 事件传输：

```json
{
  "type": "CUSTOM",
  "name": "ui.surface.create",
  "value": {
    "surfaceId": "surface_01",
    "dataRef": "result_17",
    "components": [
      {
        "id": "city-stat",
        "type": "Chart",
        "props": {
          "subType": "bar",
          "title": "各城市活动次数",
          "encoding": {
            "category": "city",
            "value": "count"
          }
        }
      }
    ]
  }
}
```

建议将自定义事件命名固定为：

```text
ui.surface.create
ui.surface.update
ui.surface.remove
ui.data.update
```

其他 AG-UI Client 即使不认识这些扩展事件，也仍然可以正常消费标准文本和工具事件。

参考：[AG-UI 与生成式 UI](https://docs.ag-ui.com/concepts/generative-ui-specs)。

## 4. 当前实现的主要问题

### 4.1 事件没有按 run 隔离

`DefaultAgentEventBus` 是进程级 multicast。`ChatController` 对 UI 和 Tool 事件只按事件类型过滤，没有按当前 `runId`、`conversationId` 或用户过滤。

与此同时，`ToolStartEvent`、`ToolEndEvent`、`UiCreateEvent` 自身也不携带运行上下文。并发运行时，一个用户的 SSE 连接可能收到另一个用户产生的 Tool/UI 事件。

这是正式部署前的阻断问题。升级到 Spring AI Alibaba 时不应复用这套全局事件总线，而应让 Graph/ReactAgent 的每次运行产生独立事件流，再由 `agent-client` 的 AG-UI Adapter 按 threadId/runId 输出。

### 4.2 ResultStore 没有用户、租户和会话授权

`StoredMcpResult` 已预留 `conversationId` 和 `runId`，但 `DynamicMcpToolCallback` 实际使用的是不带上下文的 `save(serverCode, toolName, result)`，因此保存的数据没有运行归属。

`GET /api/results/{resultRef}` 也没有验证当前用户是否拥有该结果。目前主要依靠随机 `resultRef` 防止枚举，不足以构成正式的访问控制。

生产实现至少需要把以下信息和结果一起保存：

```text
tenantId
userId
threadId
runId
toolCallId
serverCode
toolName
createdAt
expiresAt
classification / sensitivity
```

读取结果时必须用服务端认证身份校验归属，不能信任前端 `forwardedProps` 中的用户身份。

### 4.3 Tool 日志可能泄露完整结果

`DynamicMcpToolCallback` 在 `ToolEndEvent` 中附带最长 20,000 字符的序列化结果，`ChatController` 又把它作为 `detail` 发送给浏览器执行日志。

这与“完整数据只存 ResultStore”和“日志不得输出敏感数据”的目标冲突。正式实现的 Tool 事件应只发送摘要、状态、耗时、错误码和 `resultRef`，完整结果只能通过受授权的结果接口获取。

### 4.4 Schema 示例与 Schema 定义冲突

`mcp-result.schema.json` 中的 `summary`、`resultMeta`、`error` 都通过 `$ref` 指向 object 类型，但示例将这些字段设置为 `null`。因此示例不能通过该 Schema 自身的校验。

契约需要统一选择：

- 允许缺省；或者
- 显式允许 `null`；或者
- 始终返回空对象。

不应继续保持“定义不允许 null，但正式示例返回 null”的状态。

### 4.5 根对象约束不足

根对象当前只要求：

```json
"required": ["specVersion", "success"]
```

因此 `success=true` 时可以完全没有 `data` 和 `presentation`。如果平台可以约束 MCP 工具，建议通过条件 Schema 明确：

- 成功时要求 `data`、`presentation`，并禁止非空 `error`。
- 失败时要求 `error`，并要求 `data=null`。
- `presentation.mode=NONE` 时要求 `views=[]`。
- `presentation.mode=REQUIRED` 时要求至少一个 view。

### 4.6 options 白名单没有真正执行

Schema 描述称 `options` 只能使用受控白名单，但实际设置为：

```json
"additionalProperties": true
```

这只是文字约定，不是结构约束。当前 Renderer 对 options 使用较少，所以风险暂时有限；以后扩展交互或样式能力时，应按 View 类型定义明确属性并关闭额外字段。

### 4.7 Table mapping 无法端到端工作

表格 Renderer 希望接收：

```json
{
  "columns": [
    {"field": "city", "label": "城市"},
    {"field": "count", "label": "次数"}
  ]
}
```

但 Java `ViewHint.mapping()` 的类型是 `Map<String, String>`，无法表达 `Column[]`。`PresentationValidator` 还会把每个 mapping value 都当成一个数据字段名检查，同样不能处理列数组。

需要在契约层选择一种明确方案，例如：

```text
方案 A：为每种 ViewHint 定义强类型 mapping
方案 B：mapping 使用 Map<String, Object>，再按 type 做专用校验
```

建议优先采用方案 A，因为其可验证性、IDE 类型提示和跨语言模型生成能力更好。

### 4.8 其他契约问题

- `subType` 只有描述，没有枚举约束。
- 开发文档使用小写 `recommended`，Schema 和 Java 使用大写 `RECOMMENDED`。
- `PresentationValidator` 只检查第一行数据，无法发现后续行缺少字段或类型异常。
- `DynamicMcpToolCallback` 没有真正执行 JSON Schema 校验，只执行 Jackson 转换。
- Schema 允许多种 `data` 类型，但现有 Renderer 基本只支持数组或部分 `{rows: []}` 结构。
- `components[]` 在模型中是数组，但 `UiSurfacePart` 实际只渲染第一个组件。
- `UI_UPDATE` 已定义，但浏览器流和 UI SDK 尚未完成消费。

## 5. 以 Spring AI Alibaba 为主运行时的推荐架构

```text
                         ┌──────────────────────────────┐
                         │ Vue / @ac/agent-ui           │
                         │ 标准 AG-UI + Rich UI Renderer│
                         └──────────────▲───────────────┘
                                        │ 同一 AG-UI 协议
                       ┌────────────────┴────────────────┐
                       │                                 │
        ┌──────────────┴──────────────┐   ┌──────────────┴──────────────┐
        │ agent-client                │   │ agentscope-client           │
        │ Spring AI Alibaba Runtime   │   │ AgentScope v2 Java Runtime  │
        │ 自研 SAA→AG-UI Adapter      │   │ AgentScope AguiAgentAdapter │
        └──────────────▲──────────────┘   └──────────────▲──────────────┘
                       │                                 │
                       └────────────────┬────────────────┘
                                        │ 相同公共能力
                         ┌──────────────┴───────────────┐
                         │ mcp-contract + rich-ui-core  │
                         │ ResultStore + Presentation  │
                         │ ac.rich-ui Profile          │
                         └──────────────▲───────────────┘
                                        │ MCP
                         ┌──────────────┴───────────────┐
                         │ 受控/第三方 MCP Tool         │
                         └──────────────────────────────┘
```

两个 Client 工程是并列关系：

- `agent-client` 是正式产品实现，主 Runtime 为 Spring AI Alibaba。
- `agentscope-client` 是独立验证实现，主 Runtime 为 AgentScope v2 Java。
- 两者不能互相依赖，也不能通过桥接 Starter 把一个 Runtime 包进另一个 Runtime。
- 两者复用相同的 MCP Rich Result 契约、公共处理器、ResultStore SPI、PresentationService、UI Profile 和前端 SDK。

### 5.1 agent-client 的保留职责

`agent-client` 不应被删除，它仍然是面向浏览器的 Agent Host。需要调整的是内部 Agent 实现：

| 职责 | 处理方式 |
|---|---|
| Agent 推理和工具循环 | 改由 Spring AI Alibaba `ReactAgent` 承担 |
| 工作流、多 Agent、状态和 HITL | 使用 Graph Runtime/Agent Framework |
| MCP 富结果拦截 | 使用 ToolInterceptor 或 ToolCallback 包装器 |
| ResultStore | 保留，但改成 run/user/tenant scoped |
| Observation 压缩 | 保留并接入工具结果返回链路 |
| `ui_render` | 保留为 ReactAgent 本地 Tool |
| PresentationRuntime | 保留，并产生 run-scoped PresentationEvent |
| SSE Controller | 改造成正式 AG-UI Gateway |
| 全局 EventBus | 替换为 run-scoped 事件桥接 |

### 5.2 Spring AI Alibaba Rich Result 扩展点

#### ToolInterceptor / ToolCallback 包装器

在 MCP Tool 调用结束后执行：

1. 优先读取 MCP `structuredContent`。
2. 判断是否符合平台 `McpResult`。
3. 校验 `specVersion` 和 JSON Schema。
4. 保存完整结果，并绑定 `tenantId/userId/threadId/runId/toolCallId`。
5. 用摘要 Observation 替换返回给 `ReactAgent` 的完整结果。
6. 对 AG-UI Tool Result 只暴露摘要、错误码和 `resultRef`。

Spring AI Alibaba 提供 ToolInterceptor、AgentHook、ModelHook 等扩展能力，Rich Result 应放在这些扩展点，不应侵入 Graph Runtime 核心。

#### ui_render 本地工具

`ui_render(resultRef, viewId)` 继续作为本地 Tool 注册到 `ReactAgent`。调用时：

1. 从当前 Graph/Run Context 获取认证用户、threadId 和 runId。
2. 按归属读取 ResultStore。
3. 校验 viewId、mapping、数据类型和权限。
4. 生成 `SurfaceSpec`。
5. 向当前 run 的事件流发布 `PresentationEvent`。
6. AG-UI Gateway 将其编码为 `CUSTOM name=ui.surface.create`。

不要再让 `ui_render` 向进程级 multicast EventBus 发布事件。

### 5.3 AG-UI Adapter 的现实边界

截至本文编写时间，Spring AI Alibaba 官方仓库仍没有开箱即用的 AG-UI Server/Starter，相关原生支持仍处于需求讨论状态。因此，本工程需要保留一个独立的 AG-UI 适配层，把 ReactAgent/Graph 输出转换为标准事件。

该适配层只负责：

- 解析 `RunAgentInput`。
- 建立 threadId/runId 与 Graph Context 的映射。
- 转换 Run、Text、Tool、State、Reasoning 和错误事件。
- 将 PresentationEvent 转换为 AG-UI `CUSTOM`。
- 处理取消、断连、HITL 恢复和唯一终态。

它不负责模型推理、工具循环和多 Agent 编排。

参考：[Spring AI Alibaba AG-UI 原生支持需求](https://github.com/alibaba/spring-ai-alibaba/issues/4424)。

## 6. AgentScope v2 Java 独立验证工程

为了验证公共代码确实可以移植，需要在根工程下新增一个与 `agent-client` 同级的 `agentscope-client` 应用。它不是 `agent-client` 的子模块适配层，也不是 Spring AI Alibaba Graph 中的 Agent 节点。

```text
ai-mcp-platform/
├── mcp-contract/               # 公共协议
├── rich-ui-core/               # 公共富结果与 Presentation 核心
├── rich-ui-mcp-adapter/        # 公共 MCP 结果适配
├── ag-ui-protocol/             # 公共 AG-UI/Profile 模型与测试样例
├── agent-client/               # Spring AI Alibaba 实现
├── agentscope-client/          # AgentScope v2 Java 独立实现
├── packages/agent-ui/          # 公共前端 SDK
└── frontend/                   # 可选择连接任一 Client
```

### 6.1 依赖边界

`agentscope-client` 只能依赖：

- AgentScope v2 Java 的核心、MCP、AG-UI 或 Spring Boot 集成模块。
- `mcp-contract`。
- `rich-ui-core`。
- `rich-ui-mcp-adapter`。
- `ag-ui-protocol` 中的公共 Profile、测试样例或必要模型。
- WebFlux/MVC、存储、JSON Schema Validator 等通用基础设施。

明确禁止：

- `spring-ai-alibaba-starter-agentscope`。
- `spring-ai-alibaba-agent-framework`。
- `spring-ai-alibaba-graph-*`。
- `runtime-saa-adapter`。
- 通过传递依赖间接引入任何 `com.alibaba.cloud.ai.*` Runtime 类。
- 依赖 `agent-client` 的实现类。

可以通过 Maven Enforcer、依赖树检查和 ArchUnit 测试固化这些规则。

### 6.2 agentscope-client 的职责

`agentscope-client` 与 `agent-client` 提供相同的外部能力：

| 能力 | agentscope-client 实现 |
|---|---|
| Agent Runtime | AgentScope v2 `ReActAgent` 或 `HarnessAgent` |
| MCP Tool | AgentScope Toolkit/MCP Client |
| Tool 拦截 | AgentScope v2 `MiddlewareBase.onActing` 或 AgentTool Decorator |
| 运行上下文 | AgentScope `RuntimeContext` |
| `ui_render` | 注册到 AgentScope Toolkit 的本地 Tool |
| UI 事件 | AgentScope `CustomEvent`，名称为 `ui.surface.*` |
| AG-UI | AgentScope v2 `AguiAgentAdapter`/AG-UI Spring Boot Starter |
| Rich Result | 调用公共 `RichToolResultProcessor` |
| ResultStore | 公共 SPI 的独立或共享实现 |
| Result API | 与 `agent-client` 相同的授权语义和响应契约 |

参考：[AgentScope Java v2 AG-UI 集成](https://java.agentscope.io/v2/zh/integration/protocol/agui)。

### 6.3 验证方式

前端应通过配置切换两个后端：

```text
SAA_MODE        → agent-client
AGENTSCOPE_MODE → agentscope-client
```

对两个后端执行完全相同的用例：

1. 纯文本回复。
2. MCP Tool 成功和业务失败。
3. Tool 参数增量和 Tool Result。
4. 图表、表格、时间线和关系图。
5. `ui.surface.create/update/remove`。
6. resultRef 获取、过期和越权。
7. 并发 thread/run 隔离。
8. 取消、异常和唯一终态。

两个后端的模型推理文本不要求逐字一致，但以下内容必须一致：

- AG-UI 标准事件结构和生命周期约束。
- `McpResult` 解析结论。
- Observation 的结构和安全边界。
- `SurfaceSpec` 和 `ac.rich-ui` Profile。
- Result API 契约及授权语义。
- 前端 Renderer 行为。

### 6.4 为什么不使用 spring-ai-alibaba-starter-agentscope

使用该 Starter 会把 AgentScope 包装进 Spring AI Alibaba Graph，无法证明公共代码脱离 SAA 后仍可工作，还会模糊 Tool Loop、Memory、Checkpoint、HITL 和事件所有权。

独立 `agentscope-client` 可以形成更严格的可移植性证明：

```text
同一公共核心
    ├── 运行在 Spring AI Alibaba 上
    └── 运行在 AgentScope v2 Java 上
```

只有两个独立 Runtime 都能通过同一套契约和前端测试，才能认定抽取出的代码具备真实可移植性。

## 7. 运行时选择原则

| 场景 | 推荐方式 |
|---|---|
| 本工程的新主 Agent | Spring AI Alibaba `ReactAgent` |
| Java 工作流和多 Agent 编排 | Spring AI Alibaba Graph |
| 验证 AgentScope v2 Java 可移植性 | 新建独立 `agentscope-client`，只依赖 AgentScope v2 和公共模块 |
| 已有 AgentScope Java 系统 | 将公共模块和 AgentScope Adapter 引入其自身工程，保持 Runtime 独立 |
| 只需要复用当前富可视化能力 | 移植 Rich Result 扩展，不替换 Agent Runtime |
| 浏览器统一协议 | 标准 AG-UI + `CUSTOM ui.surface.*` |

`agent-client` 与 `agentscope-client` 分别管理自己的 Tool Loop、Memory、Checkpoint 和 HITL 状态。两者通过共同协议和测试保持等价，不在同一条执行链中嵌套 Runtime。

## 8. 前端迁移方案

### 8.1 可以保留的部分

- `RichMessage.parts[]`
- `TextPart` 与 `UiPart` 交错展示
- `UiSurfacePart`
- Renderer Registry
- Chart、Table、Timeline、RelationGraph Renderer
- Result 加载时的 loading/error 状态

### 8.2 需要替换的部分

当前 `packages/agent-ui/src/core/stream.ts` 解析的是项目自定义事件。接入 Spring AI Alibaba 版 `agent-client` 后应改为消费标准 AG-UI：

| AG-UI 事件 | UI 行为 |
|---|---|
| `RUN_STARTED` | 创建本轮运行状态 |
| `TEXT_MESSAGE_START` | 创建 Assistant TextPart |
| `TEXT_MESSAGE_CONTENT` | 按 `messageId` 追加 delta |
| `TEXT_MESSAGE_END` | 结束文本块 |
| `TOOL_CALL_START/ARGS/END` | 更新执行日志 |
| `TOOL_CALL_RESULT` | 记录摘要、错误或 resultRef |
| `CUSTOM ui.surface.create` | 插入 UiPart |
| `CUSTOM ui.surface.update` | 按 surfaceId 更新 UiPart |
| `CUSTOM ui.surface.remove` | 删除或标记 UiPart |
| `RUN_FINISHED` | 结束运行 |
| `RUN_ERROR` | 标记运行失败 |
| `subagent.*` | 更新多 Agent 执行面板 |

前端请求也应改为标准 `RunAgentInput`，由前端生成或维护 `threadId/runId`，而不是只发送 `{conversationId, message}`。

### 8.3 Result API 仍然可以保留

AG-UI 没有规定 `resultRef` 必须如何解析，因此可以继续保留独立接口，例如：

```http
GET /api/results/{resultRef}
```

但需要补充：

- 用户、租户和 thread 归属校验。
- 过期策略和历史消息展示策略。
- Redis、数据库或对象存储等分布式实现。
- 数据分类、脱敏和审计。
- 防止浏览器缓存敏感结果的 Cache-Control。
- 单结果大小、租户容量和访问频率限制。

小数据可以直接放进 `CUSTOM.value`，大数据或敏感数据继续使用 `dataRef`。两者可以根据大小和安全级别选择。

## 9. MCP 工具返回契约策略

### 9.1 受控 MCP Tool

对于由平台控制的 MCP Tool，可以强制要求：

- 完整业务结果放在 `structuredContent`。
- `structuredContent` 符合 `mcp-result.schema.json`。
- 始终返回明确的 `specVersion`。
- MCP 协议或工具执行异常使用 `CallToolResult.isError`。
- 可预期的业务失败使用 `success=false + error`。
- `summary.highlights` 必须是服务端确定性计算的事实。
- 聚合、过滤、排序和统计应在业务服务端完成。
- `presentation` 只能返回语义映射和受控选项。
- `content` 只提供简短人类可读摘要，不重复完整数据。

Agent Host 收到结果后仍必须再次校验，不能因为 MCP Server 是内部服务就完全信任结果。

### 9.2 第三方或不可控 MCP Tool

不应要求所有第三方 MCP Tool 使用平台私有 envelope，否则会失去通用 MCP 兼容性。推荐增加适配层：

```text
第三方 CallToolResult
    ↓
按 serverCode/toolName 选择 ResultAdapter
    ↓
平台内部 RichResult
    ↓
ResultStore + Observation + Presentation
```

适配器可以采用以下策略：

- 已知工具：配置字段映射、摘要算法和 ViewHint。
- 未知但有 structuredContent：保存原始结构，只生成通用摘要，不默认生成 UI。
- 只有 text：作为普通 Tool Result 交给 Agent，不进入富可视化链路。
- 结果过大：保存原始结果，生成截断摘要和 resultRef。
- 无法校验：降级为普通工具结果，而不是让整个 Agent run 失败。

## 10. 模块迁移边界

### 10.1 建议保留或重写为 Spring AI Alibaba 扩展

- `mcp-result.schema.json`
- `McpResult`/`PresentationHint`/强类型 `ViewHint`
- `ResultStore` 抽象
- `ObservationBuilder` 思想
- `PresentationValidator`
- `PresentationMapper`
- `SurfaceSpec`
- `ui_render` 工具语义
- Vue Renderer Registry
- Chart/Table/Timeline/RelationGraph Renderer

### 10.2 建议由 Spring AI Alibaba 替代或重构

- `AgentFactory`
- 直接驱动 Agent Loop 的 Spring AI `ChatClient`

- 当前仅依赖 ChatMemory 的运行状态管理

`agent-client` 模块本身应保留；被替代的是其中的 Agent 执行核心和事件模型，而不是 ResultStore、PresentationRuntime、结果接口及 AG-UI Gateway 职责。

## 11. 推荐实施顺序

### 阶段一：协议边界整理

1. 修正 `mcp-result.schema.json` 的 null、required、mapping 和 options 问题。
2. 定义强类型 Chart/Table/Timeline/RelationGraph mapping。
3. 定义 `ui.surface.*` 自定义事件契约。
4. 明确 ResultStore 的租户、用户、thread 和 run 归属。

验收标准：Schema 可以校验全部正式示例，并能拒绝字段类型错误、非法 ViewHint 和越权结果读取。

### 阶段二：Spring AI Alibaba Agent 化

1. 使用兼容 BOM 引入 Spring AI Alibaba Agent Framework。
2. 将当前 `ChatClient` 执行核心替换为 `ReactAgent`。
3. 把 MCP Tool 和 `ui_render` 注册到 ReactAgent Toolkit。
4. 使用 ToolInterceptor/工具包装器实现 MCP ResultAdapter。
5. 接入带认证上下文的 ResultStore 和 Observation 压缩。
6. 让 `ui_render` 向当前 run 发布 PresentationEvent。

验收标准：Spring AI Alibaba ReactAgent 能完成“查数据 → 摘要给模型 → 决定出图 → 发布 PresentationEvent”，且不再依赖进程级全局事件总线。

### 阶段三：正式 AG-UI 接入

1. 在 `agent-client` 中实现 Spring AI Alibaba/Graph 到 AG-UI 的运行时适配器。
2. 请求改为 `RunAgentInput`。
3. 使用标准 Run/Text/Tool/State 事件。
4. 将 PresentationEvent 转换为标准 `CUSTOM`。
5. 检查并发运行隔离、取消、错误终态和断开行为。

验收标准：标准 AG-UI Client 能消费文本、工具和生命周期事件；不认识 `ui.surface.*` 的客户端仍能正常显示文本回答。

### 阶段四：独立 agentscope-client 验证

1. 新建与 `agent-client` 同级的 `agentscope-client` Maven 模块。
2. 只引入 AgentScope v2 Java 及公共模块，禁止引入 Spring AI Alibaba。
3. 使用 AgentScope Middleware/Toolkit 接入公共 Rich ResultAdapter 和 `ui_render`。
4. 使用 AgentScope 自带 AG-UI Adapter 输出正式事件。
5. 与 `agent-client` 执行同一套契约、前端、安全和并发测试。

验收标准：`agentscope-client` 不包含 SAA 依赖，仍能独立完成“AG-UI 对话 → MCP 富结果 → resultRef → ui_render → CUSTOM Surface → 前端渲染”的完整闭环。

### 阶段五：前端适配

1. 为 `@ac/agent-ui` 增加 AG-UI Stream Adapter。
2. 按 messageId/toolCallId/surfaceId 更新状态。
3. 支持 `ui.surface.update/remove`。
4. 增加子 Agent 执行面板和 HITL UI。
5. 增加断线、过期结果和历史消息降级展示。

验收标准：文本、工具调用和 UI 部件能够按照事件发生顺序交错显示，多 Agent 和并发会话之间不串流。

## 12. 最终建议

这套工程最值得保留的是“数据、模型决策、展示运行时和前端渲染器四层分离”的机制。`agent-client` 应继续作为 Host，但其执行核心应从手写 Spring AI `ChatClient` 编排升级为 Spring AI Alibaba Agent Framework。

目标架构应当是：

> `agent-client` 使用 Spring AI Alibaba Runtime，`agentscope-client` 使用 AgentScope v2 Java Runtime；二者分别独立运行，共用 Rich Result、Presentation、AG-UI Profile 和 Vue Renderer 契约，以双实现验证可移植性。

这种拆分具有以下好处：

- 不在 `ChatController` 和全局 EventBus 中重复实现 Spring AI Alibaba 已具备的 Agent Loop、Graph、Memory、多 Agent 和 HITL 能力。
- 保留当前工程避免大数据进入 LLM 的优势。
- 保留现有 Vue 可视化组件投资。
- 受控 MCP Tool 和第三方 MCP Tool 都可以接入。
- AgentScope 验证工程完全不依赖 Spring AI Alibaba，能够发现公共代码中的隐性 Runtime 耦合。
- 标准 AG-UI Client 与项目自定义富 UI 可以同时工作。
- 后续需要跨客户端 UI 互操作时，可以再将 `SurfaceSpec` 适配为 A2UI、MCP-UI 或其他生成式 UI 标准。

## 13. 面向三个硬性目标的详细实施方案

### 13.1 总体分层

为避免公共能力被某一个 Agent Runtime 绑定，建议把工程拆成以下逻辑层。模块名可以在实施时调整，但依赖方向必须保持单向：

```text
                          ┌─────────────────────────┐
                          │ frontend / agent-ui     │
                          │ AG-UI Client + Renderer │
                          └────────────▲────────────┘
                                       │ 相同 AG-UI HTTP/SSE
                    ┌──────────────────┴──────────────────┐
                    │                                     │
       ┌────────────┴─────────────┐         ┌─────────────┴────────────┐
       │ agent-client             │         │ agentscope-client       │
       │ SAA Runtime + AG-UI Web  │         │ AS v2 Runtime + AG-UI   │
       └────────────▲─────────────┘         └─────────────▲────────────┘
                    │ runtime-saa-adapter                 │ runtime-agentscope-v2
                    └──────────────────┬──────────────────┘
                                       │ Rich UI SPI
                          ┌────────────┴────────────┐
                          │ rich-ui-core            │
                          │ Result/Observation/UI   │
                          └────────────▲────────────┘
                                       │ Contract types
                          ┌────────────┴────────────┐
                          │ mcp-contract            │
                          │ JSON Schema + DTO       │
                          └─────────────────────────┘
```

推荐模块及职责如下：

| 模块 | 职责 | 禁止依赖 |
|---|---|---|
| `mcp-contract` | `McpResult`、强类型 ViewHint、SurfaceSpec、JSON Schema | SAA、AgentScope、Web、具体存储 |
| `rich-ui-core` | 结果处理、Observation、Presentation 校验、ResultStore SPI、运行上下文 SPI | SAA、AgentScope、Spring MVC/WebFlux |
| `rich-ui-mcp-adapter` | MCP `CallToolResult` 到内部 RichResult 的解析与适配 | SAA、AgentScope |
| `ag-ui-protocol` | `RunAgentInput`、标准 Event 模型、编码与顺序校验 | SAA、AgentScope、业务 Tool |
| `ag-ui-spring-web` | HTTP/SSE Endpoint、认证上下文、取消和 Result API | 具体 Agent 实现 |
| `runtime-saa-adapter` | SAA ReactAgent/Graph、ToolInterceptor、Graph 事件转换 | AgentScope |
| `runtime-agentscope-v2` | AgentScope v2 Middleware、Toolkit、CustomEvent 转换 | Spring AI Alibaba |
| `agent-client` | 组装 SAA Runtime、SAA Adapter、AG-UI Web 与公共模块 | AgentScope |
| `agentscope-client` | 组装 AgentScope v2、AgentScope Adapter、AG-UI 与公共模块 | Spring AI Alibaba、`agent-client` |
| `packages/agent-ui` | 标准 AG-UI 客户端适配、消息 reducer、Surface Renderer | Java Runtime |

`ag-ui-spring-web` 可以被两个工程共同复用，也可以在 `agentscope-client` 中使用 AgentScope 官方 AG-UI Starter。无论采用哪种 Web 入口，对外事件和 `ac.rich-ui` Profile 都必须通过同一套协议测试。

### 13.2 公共核心接口

公共层需要围绕“数据处理”和“运行事件”定义自己的最小 SPI，不能直接把 Spring AI `ToolCallback`、SAA Graph 类型或 AgentScope `AgentEvent` 暴露出来。

建议至少包含以下抽象：

```java
public record RunScope(
        String tenantId,
        String userId,
        String threadId,
        String runId,
        String toolCallId) {
}

public interface RichToolResultProcessor {
    ProcessedToolResult process(
            RunScope scope,
            ToolIdentity tool,
            RawToolResult result);
}

public interface ResultStore {
    ResultReference save(RunScope scope, ToolIdentity tool, McpResult<?> result);
    StoredMcpResult getAuthorized(ResultReference ref, AccessSubject subject);
}

public interface ObservationBuilder {
    AgentObservation build(ResultReference ref, McpResult<?> result);
}

public interface PresentationService {
    SurfaceSpec render(RunScope scope, String resultRef, String viewId);
}

public interface RuntimeEventSink {
    void publish(RunScope scope, RichRuntimeEvent event);
}
```

这些接口只是设计形态，实施时可以使用 record、sealed interface 或泛型优化，但必须满足：

- 输入输出都是项目自有类型。
- 所有操作显式携带 `RunScope`。
- ResultStore 读取必须经过授权，而不是只有 `get(resultRef)`。
- `PresentationService` 不直接依赖 SSE。
- Runtime Adapter 负责把框架事件转换成 `RichRuntimeEvent`，AG-UI 层再负责协议编码。

### 13.3 工具结果的统一处理流水线

Spring AI Alibaba 和 AgentScope v2 必须共用下面这一条流水线：

```text
Runtime 原生 Tool Result
    ↓ Runtime Tool Adapter
RawToolResult
    ↓ RichToolResultProcessor
识别协议错误 / 业务错误 / 普通结果 / 富结果
    ↓
JSON Schema 校验
    ↓
ResultStore.save(RunScope, ToolIdentity, McpResult)
    ↓
ObservationBuilder
    ↓
ProcessedToolResult(observation, resultRef, publicSummary)
    ↓
返回 Agent Runtime，并发布不含完整数据的 Tool Event
```

处理结果至少分为四类：

| 类型 | 行为 |
|---|---|
| MCP `isError=true` | 转换为协议/执行错误，不伪装为成功业务结果 |
| `McpResult.success=false` | 保存必要审计信息，向 Agent 返回可理解的业务错误 |
| 合法 Rich Result | 保存完整数据，向 Agent 返回压缩 Observation |
| 普通第三方 Tool Result | 原样或按适配策略返回，不强制进入 Presentation 流程 |

### 13.4 Spring AI Alibaba Runtime Adapter

`runtime-saa-adapter` 是当前 `agent-client` 的主适配器，实施重点如下。

#### Agent 构建

- 使用 Spring AI Alibaba `ReactAgent` 替代当前 `AgentFactory.create()` 返回的 `ChatClient`。
- 使用 Graph Runtime 的 thread/checkpoint 标识承载 AG-UI `threadId` 和 `runId`。
- MCP Tool 与 `ui_render` 作为 ReactAgent 的正式工具注册。
- Memory、HITL、Tool 重试、上下文压缩等使用 SAA 能力，不在 Controller 重复实现。

#### Tool 结果拦截

- 优先使用 SAA ToolInterceptor；若当前版本无法安全改写 Tool Result，则使用 ToolCallback Decorator。
- Adapter 把 SAA 的 Tool 输入、输出和运行上下文转换为公共层的 `RunScope`、`ToolIdentity` 和 `RawToolResult`。
- 公共层返回的 Observation 再转换回 SAA 可接受的 Tool Result。
- 完整 `McpResult.data` 不进入模型消息、AG-UI Tool Result 和普通应用日志。

#### 运行事件转换

建立 SAA/Graph 到内部事件的显式映射：

| SAA/Graph 语义 | 内部事件 |
|---|---|
| Graph run 开始 | `RunStarted` |
| Assistant 消息开始 | `TextMessageStarted` |
| Token/chunk | `TextMessageContent` |
| Assistant 消息结束 | `TextMessageEnded` |
| Tool 选择 | `ToolCallStarted` |
| Tool 参数 | `ToolCallArgs` |
| Tool 执行结束 | `ToolCallEnded` |
| 压缩后的 Tool Result | `ToolCallResult` |
| `ui_render` 成功 | `SurfaceCreated` |
| Graph 正常终止 | `RunFinished` |
| Graph 异常终止 | `RunError` |

转换层必须保留 messageId、toolCallId、threadId 和 runId，不能只依靠事件到达顺序推断归属。

### 13.5 AgentScope v2 Java Adapter

`runtime-agentscope-v2` 只适配公共 SPI，不复制公共实现，并由独立的 `agentscope-client` 应用组装和运行。该 Adapter 及应用的依赖树中不得出现 Spring AI Alibaba。

AgentScope v2 可使用的主要扩展点是：

- `MiddlewareBase.onAgent`：注入和清理本次 `RunScope`，观察完整运行生命周期。
- `MiddlewareBase.onActing`：观察内部 Tool 执行并转换 Tool Result。
- `RuntimeContext`：在 middleware、tool 和 ResultStore 之间传递 userId/sessionId/threadId/runId。
- `Toolkit`/`AgentTool`：注册 `ui_render`。
- `CustomEvent`：发布 `ui.surface.create/update/remove`。
- AgentScope 自带 `AguiAgentAdapter`：独立部署时输出标准 AG-UI。

`agentscope-client` 的建议组装结构：

```text
agentscope-client
├── AgentScope v2 ReActAgent/HarnessAgent
├── AgentScope Toolkit + MCP Client
├── runtime-agentscope-v2
├── mcp-contract
├── rich-ui-core
├── rich-ui-mcp-adapter
├── AgentScope AguiAgentAdapter
└── Result API / Security / application.yml
```

它应有独立端口和独立配置，前端通过环境变量或运行时配置选择 `agent-client` 或 `agentscope-client`。验证期间两个应用可以连接同一个 MCP Server，但各自维护独立的 Agent 状态和 ResultStore 命名空间。

参考：

- [AgentScope v2 Middleware](https://java.agentscope.io/v2/zh/docs/building-blocks/middleware.html)
- [AgentScope v2 Tool 与 RuntimeContext](https://java.agentscope.io/v2/zh/docs/building-blocks/tool.html)
- [AgentScope v2 AG-UI](https://java.agentscope.io/v2/zh/integration/protocol/agui)

Adapter 的处理流程为：

```text
AgentScope ActingInput / AgentEvent
    ↓
AgentScopeRichToolMiddleware
    ↓ 转换为公共类型
RichToolResultProcessor
    ↓
ProcessedToolResult
    ↓ 转换回 AgentScope 类型
ToolResultBlock / CustomEvent
```

AgentScope Adapter 的验收标准不是“代码大致相似”，而是：输入同一份 MCP Rich Result 时，SAA 和 AgentScope 两个 Adapter 最终生成语义一致的 Observation、ResultReference 和 `ui.surface.create` payload。

### 13.6 正式 AG-UI Server

`ag-ui-protocol` 和 `ag-ui-spring-web` 共同承担正式兼容，不能继续使用当前 `delta/tool/ui/done` 外部协议。

#### 输入

入口接收完整 `RunAgentInput`，至少正确处理：

```text
threadId
runId
parentRunId
messages
state
tools
context
forwardedProps
resume（若采用支持该字段的协议版本）
```

客户端提供的身份字段不可信。tenantId/userId 必须由服务端认证链路注入，threadId 必须校验归属。

#### 输出顺序

一次成功运行的最小事件序列为：

```text
RUN_STARTED
TEXT_MESSAGE_START
TEXT_MESSAGE_CONTENT × N
TEXT_MESSAGE_END
RUN_FINISHED
```

带工具调用的序列为：

```text
TOOL_CALL_START
TOOL_CALL_ARGS × N
TOOL_CALL_END
TOOL_CALL_RESULT
```

UI 使用：

```text
CUSTOM name=ui.surface.create
CUSTOM name=ui.surface.update
CUSTOM name=ui.surface.remove
```

终态规则：

- 每个 run 必须有且只有一个终态。
- 正常结束发送 `RUN_FINISHED`。
- 异常结束发送 `RUN_ERROR`。
- `RUN_ERROR` 后不能再补一个伪成功的 `RUN_FINISHED`。
- 客户端取消需要终止对应 run，不能影响其他 run。

#### SSE 编码

- Content-Type 使用 `text/event-stream`。
- 每个 `data:` frame 包含一个合法 AG-UI Event JSON。
- 事件的 `type` 使用标准大写枚举。
- 支持 SSE chunk 拆分、空行、keep-alive 和多行 data。
- 不依赖自定义 `event: delta/ui/tool/done` 才能识别事件。
- 对未知标准事件和 `CUSTOM` 事件保持前向兼容。

可以使用 AG-UI 官方 Java Core 类型减少模型漂移，但仍需通过协议契约测试确认服务端输出。参考：[AG-UI Java SDK](https://docs.ag-ui.com/sdk/java/overview)。

### 13.7 自定义 UI Profile

为了让自定义 UI 也具有稳定兼容性，应把它定义成 AG-UI 上的版本化 Profile：

```json
{
  "type": "CUSTOM",
  "name": "ui.surface.create",
  "value": {
    "profile": "ac.rich-ui",
    "profileVersion": "1.0",
    "surfaceId": "surface_01",
    "dataRef": "result_17",
    "components": []
  }
}
```

Profile 需要单独提供 JSON Schema，并规定：

- `surfaceId` 在同一 thread 中唯一。
- create 先于 update/remove。
- `dataRef` 只允许当前用户和 thread 获取。
- component type 必须来自前端白名单。
- props 必须按 component type 校验。
- 客户端不认识 profile 或版本时安全降级为文字提示。

### 13.8 前端 AG-UI Client Adapter

前端建议使用 AG-UI 官方 TypeScript Core/Client，或者严格按同一模型实现 Vue Adapter。现有 Renderer 不需要绑定 AG-UI，只需要消费 reducer 产生的 `UiSurface`。

前端内部建议分成：

```text
AG-UI transport
    ↓
AG-UI event validator
    ↓
conversation reducer
    ├── message state
    ├── tool state
    ├── run state
    └── surface state
         ↓
Renderer Registry
```

Reducer 必须按 ID 更新状态：

- `messageId` 关联文本 START/CONTENT/END。
- `toolCallId` 关联工具 START/ARGS/END/RESULT。
- `runId` 关联生命周期和取消。
- `surfaceId` 关联 UI create/update/remove。

不能再把“当前最后一条 Assistant 消息”作为所有事件的隐式归属。

### 13.9 可移植性约束

为了保证公共代码确实可迁移，而不是名义上可迁移，应设置以下工程约束：

- `mcp-contract`、`rich-ui-core`、`rich-ui-mcp-adapter` 不允许依赖 `com.alibaba.cloud.ai.*`。
- 同样不允许依赖 `io.agentscope.*`。
- 公共层不依赖 Spring MVC/WebFlux Controller。
- 公共层不持有全局静态运行上下文。
- 所有存储键和事件都显式携带 RunScope。
- SAA 与 AgentScope Adapter 使用同一套公共契约测试样例。
- 两个 Adapter 产生的 `ui.surface.*` payload 必须通过同一 JSON Schema。
- Runtime 升级只允许修改对应 Adapter，不应修改 Renderer 和业务 MCP Tool。

可以在 Maven Enforcer、ArchUnit 或模块依赖测试中固化这些边界。

### 13.10 安全与生产化

正式 AG-UI 和跨 Runtime 可移植都不能建立在当前匿名 ResultStore 上。实施时还需要：

- 使用认证主体构造 `AccessSubject`，禁止从 `forwardedProps` 信任 userId。
- ResultReference 至少绑定 tenant/user/thread/run，并设置 TTL。
- Result API 做对象级授权，防止 IDOR。
- Tool Event、AG-UI Event、应用日志和 Trace 不记录完整业务数据。
- 对 summary/highlights 执行脱敏和长度限制。
- 分布式部署时使用 Redis/数据库/对象存储实现 ResultStore。
- 为断线、重试和重复请求定义 runId 幂等策略。
- 限制每个 run 的事件数、结果容量、组件数和更新频率。
- Renderer 只接收经过 Schema 校验的 props，不允许动态执行代码。

## 14. 验收方案

### 14.1 AG-UI 协议验收

- 使用标准 AG-UI Client 调用 `agent-client`，无需项目私有解析逻辑即可显示普通文本。
- 验证 Run、Text、Tool、State、Custom 和错误事件的字段与顺序。
- 验证每个 run 只有一个终态。
- 验证两个并发 run 不串事件。
- 验证客户端断开只取消对应 run。
- 验证未知 CustomEvent 不导致整个流失败。
- 保存典型事件流为 golden trace，并在 CI 中进行回归校验。

### 14.2 Spring AI Alibaba 验收

- `agent-client` 的 Agent 实例是 SAA `ReactAgent` 或明确的 Graph Agent，不再是直接返回 `ChatClient`。
- MCP Tool、`ui_render`、Memory、HITL 和多 Agent 流程通过 SAA Runtime 工作。
- Tool Result 经公共 RichToolResultProcessor 处理。
- Graph 的 thread/checkpoint 与 AG-UI threadId/runId 映射稳定。
- 不再使用进程级 multicast EventBus 承载用户运行事件。

### 14.3 AgentScope v2 可移植验收

准备一组相同的契约测试数据，在 SAA 和 AgentScope v2 中分别运行：

1. 普通文本 Tool Result。
2. 成功的图表 Rich Result。
3. 业务失败 Rich Result。
4. MCP `isError=true`。
5. Schema 非法结果。
6. ResultReference 过期。
7. 跨用户读取 ResultReference。
8. `ui_render` 使用非法 viewId。

两个 Runtime 应产生相同的公共层判定、相同的 Observation 语义和相同的 SurfaceSpec；允许 Runtime 原生事件类型不同，但转换后的 AG-UI 语义必须一致。

### 14.4 完成定义

同时满足以下条件才算完成：

- 标准 AG-UI Client 可以直接调用。
- `agent-client` 使用 Spring AI Alibaba Runtime。
- 公共模块不依赖 SAA 或 AgentScope。
- AgentScope v2 Adapter 有可运行示例和契约测试。
- SAA 与 AgentScope 使用同一 MCP Rich Result Schema 和 UI Profile Schema。
- 并发隔离、对象授权和敏感日志检查通过。
- 当前 Chart/Table/Timeline/RelationGraph Renderer 在新链路中可用。
