# 富可视化流式响应第二阶段实施设计

> 对应《[LLM + MCP 富可视化流式响应技术方案](LLM%20+%20MCP%20富可视化流式响应技术方案.md)》第 50 节。本文是待实施设计，不表示下述功能已经交付。以仓库当前的 `McpResult 1.1`、`ac.rich-ui/1.0` 和四种内置渲染器为基线。

## 1. 范围与决策

本期交付 `Metric`、`EntityCard`、`Tree`、`Heatmap`、`RelationshipPath`、`EvidenceChain` 六种组件；支持同一次 run 内 `ui.surface.update` 替换组件声明及完整数据快照；支持本地节点展开，以及显式声明的点击下钻。现有 Chart 点击下钻沿用《[图表点击下钻技术方案](图表点击下钻技术方案.md)》的“追问即新对话”路径，并完成宿主接线与回归。

原方案第 28 节把 `Map`、`FundFlow`、`Trajectory` 也列入“第二阶段”，第 50 节没有列出。本期以第 50 节的六种组件为交付边界；前三项进入后续专题设计，不能在本期 schema 中仅声明类型却没有映射、校验和渲染实现。

| 事项 | 本期做法 | 理由 |
|---|---|---|
| 数据更新 | 保存新的完整 `McpResult`，用新 `dataRef` 发送 `ui.surface.update`；不向 SSE 推送业务数据或 JSON Patch | 复用现有结果读取与授权链路，失败时保留旧画面 |
| Surface 更新 | 只允许创建它的同一 `threadId/runId` 更新；一次更新原子替换 `dataRef` 和/或完整 `components` 数组 | 当前 `ResultStore.get` 强制校验同一 run；前端 reducer 尚未校验更新归属 |
| 树节点展开 | 已加载节点在浏览器本地展开/收起；未加载子树通过“查看详情”发起新的对话与结果 Surface | 不跨 run 修改原 Surface，也不让浏览器直接调用 MCP |
| 图表点击 | 复用现有 Chart `drillDown` 事件，宿主调用 `useConversation.send` | 已有 Renderer 事件和独立技术方案 |
| 组件组合 | 本期每个 Surface 仍放一个组件；`components` 数组保持原协议形状 | 当前 `UiSurfacePart.vue` 只渲染 `components[0]`；多组件布局需另行设计 |

## 2. 现状与改动接点

| 层 | 已有代码 | 本期缺口 |
|---|---|---|
| MCP 契约 | `mcp-contract` 的 `ViewHint`/`ViewMapping` 为四类 sealed 类型；`mcp-result.schema.json` 为 1.1；Profile schema 为 1.0 | 六类强类型映射、schema、样例、版本迁移 |
| 核心 | `DefaultPresentationService` 授权读结果，`PresentationValidator` 校验数据，`PresentationMapper` 生成单组件 `SurfaceSpec` | 六类校验与映射；受授权的 Surface 更新服务与实例索引 |
| Runtime | 两套 `ui_render` 都只创建 Surface；`AgUiEventTranslator` 可转发 `CustomRuntimeEvent` | 两套 Runtime 提供等价的更新入口与事件发布 |
| 前端 | reducer 已识别 `ui.surface.create/update/remove`；`UiSurfacePart` 按 `dataRef` 重取数据；Registry 有四个 Renderer | 六类 Renderer、严格 props 校验、同 run 更新校验、异步结果竞争处理 |
| 交互 | `ChartRenderer` 向 `UiSurfacePart` 发 `drill-down`；Graph Renderer 尚无点击行为 | 宿主接线与失败反馈；Tree 展开；其余组件按声明决定是否可点击 |

特别注意：当前 `ui.surface.update` 的 reducer 以收到事件的 run 重建 Surface，并没有检查它是否为创建 run。若直接从后续 run 更新旧 Surface，前端会使用新的 `runId` 读取旧 `dataRef`，而结果服务会因归属不符返回 403。本期应先阻止这种更新，再考虑跨 run 能力。

## 3. 契约版本与迁移

1. 新生产者在六类 View 上使用 `McpResult.specVersion = "1.2"`。消费者继续接收 1.0/1.1；1.0 仍只用于迁移读取。1.1 四类 View 的字段语义保持不变。必须同时更新 `McpResult.CURRENT_SPEC_VERSION`、解码器、JSON Schema、Java 类型和契约文档，不允许只改 schema。
2. 六类组件及相应 `ui.surface.*` 使用 `ac.rich-ui/1.1`。现有 1.0 Surface 仍可读取和渲染；1.0 只允许四类旧组件。新版前端按版本分别校验，未知版本展示文字降级。更新事件的版本必须与目标 Surface 相同，不允许借更新事件原地升级版本。
3. 部署顺序为：先上线能读 1.1/1.2 结果与 Profile 1.0/1.1 的消费者及两个 Runtime，再启用生产者输出新类型。旧浏览器收到 1.1 Profile 时会显示“不支持版本”；因此新类型的生产需受服务端能力开关控制，待前端覆盖完成后开启。回滚只关闭新类型生产，不回写或篡改已发出的历史结果。
4. 不增加可执行配置字段。`mapping` 只引用数据字段；`options` 为有限枚举和数字白名单。沿用单个 View 的 `priority`、`title`、`description`、`drillDown` 等通用字段。

## 4. 六类 View 的数据形状

`data` 仍来自 MCP Data Tool，优先使用对象数组。下表字段名是 **mapping 的键**，右侧是对应业务行的要求；可选字段缺失或为 `null` 时不显示。所有必填字段必须在每一行存在且类型正确，不把空字符串/`null` 强转为有效 ID。数值必须为有限数。单个结果仍受 `ResultStoreLimits` 限制，视图 `options.limit` 只控制显示量，不截断原始结果。

| View `type` → 组件 | `subType` | mapping 键 | 行约束和渲染 |
|---|---|---|---|
| `metric` → `Metric` | `single` | `label`, `value`, `unit?`, `change?` | 一行一个指标；`label` 文本、`value` 数值；`unit` 文本；`change` 有限数值。默认最多 12 项，卡片格式化仅作用于显示 |
| `entity_card` → `EntityCard` | `standard` | `id`, `name`, `kind?`, `summary?` | `id`、`name` 非空文本，`id` 在结果内唯一；其余为有长度上限的纯文本。默认最多 50 张 |
| `tree` → `Tree` | `hierarchy` | `id`, `parentId`, `label`, `hasChildren?` | `id` 唯一；根的 `parentId` 为 `null`；非根必须引用结果内 `id`；无环、至少一个根；`hasChildren` 布尔值。默认最多 500 节点、最大深度 10 |
| `heatmap` → `Heatmap` | `matrix` | `x`, `y`, `value` | `x/y` 为标量维度，`value` 为有限数；`(x,y)` 组合唯一；默认最多 1000 格。无值格显示为“无数据”，不补 0 |
| `relationship_path` → `RelationshipPath` | `ordered` | `step`, `source`, `target`, `label?` | `step` 从 1 开始连续且唯一；前一步 `target` 等于后一步 `source`；节点 ID 为非空文本；默认最多 30 条边。按步骤绘制，不重新运行寻路算法 |
| `evidence_chain` → `EvidenceChain` | `ordered` | `step`, `id`, `title`, `source`, `summary?`, `evidenceRef?` | `step` 连续唯一，`id` 唯一；`title/source` 为非空文本；`evidenceRef` 为不透明业务标识，只作文本展示；默认最多 50 条。按证据顺序呈现，不推断证据真伪 |

各类型 `options` 只允许 `limit`（上表默认值与最大值）以及明确需要的显示开关：`Metric.showChange`、`EntityCard.showSummary`、`Heatmap.showLabels`、`RelationshipPath.showLabels`、`EvidenceChain.showSource`。布尔值默认 `true`；禁止颜色表达式、HTML、URL 模板、ECharts option 和 G6 配置透传。组件使用 Vue 文本插值呈现服务端字符串。

示例：

```json
{
  "specVersion": "1.2",
  "success": true,
  "data": [{"nodeId":"n1","parentNodeId":null,"nodeName":"总部","hasChildren":true},{"nodeId":"n2","parentNodeId":"n1","nodeName":"研发部","hasChildren":false}],
  "presentation": {
    "mode": "RECOMMENDED",
    "views": [{"id":"org-tree","type":"tree","subType":"hierarchy","title":"组织结构","mapping":{"id":"nodeId","parentId":"parentNodeId","label":"nodeName","hasChildren":"hasChildren"},"options":{"limit":500}}]
  }
}
```

`Tree` 的 `parentId` 是必需的 **mapping 键**，但根节点对应的 **数据值** 必须允许 `null`。目前 `PresentationValidator` 对所有映射字段逐行要求非空，不能直接复用这条通用判断；应为各映射区分必需值与可空值，再做整批结构校验。`RelationshipPath`、`EvidenceChain` 的顺序和链式约束也必须在整批校验中完成。没有数据时不构造可视 Surface，走既有文字/空结果路径。

## 5. Surface 与数据更新协议

### 5.1 后端写入和发事件

在 `rich-ui-core` 增加按 `RunScope` 管理的 `SurfaceRegistry` 和 `PresentationService.update(...)`：记录 `surfaceId → 创建者 tenant/user/thread/run、当前 dataRef、组件、revision`。`ui_render` 成功创建后登记；更新时必须验证调用者、原 Surface 和新结果属于同一 run，目标 `viewId` 存在，新结果通过 `PresentationValidator`，组件通过 `PresentationMapper` 重新生成，但保留原 `surfaceId`。检验通过后更新 Registry，再发事件；失败不发事件且旧 Surface 不变。

最小更新事件使用现有 `CUSTOM ui.surface.update` 名称；1.1 Profile 的 value 增加单调递增的 `revision`，从 create 的 `revision: 1` 开始：

```json
{
  "type": "CUSTOM",
  "name": "ui.surface.update",
  "value": {
    "profile": "ac.rich-ui",
    "profileVersion": "1.1",
    "surfaceId": "surface_01",
    "revision": 2,
    "dataRef": "result_18",
    "components": [{"id":"org-tree","type":"Tree","props":{"subType":"hierarchy","title":"组织结构","encoding":{"id":"nodeId","parentId":"parentNodeId","label":"nodeName","hasChildren":"hasChildren"},"options":{"limit":500}}}]
  }
}
```

更新是**完整快照替换**，不是合并：`components` 是整个组件数组，`dataRef` 是新的完整结果引用。即使 schema 允许二选一，写端在更换结果时应同时发送二者，避免新数据与旧映射短暂不匹配。纯标题等展示属性更新可以只发 `components`。前端对 1.1 事件按 `revision` 接收：仅接受同一 run 且恰好 `current.revision + 1`；重复或旧事件忽略，缺号时标记需重同步并保留当前快照。1.0 事件保留原处理逻辑，但加同 run 检查。

`ResultStore` 继续保存不可变结果；不得修改旧引用指向的对象。新结果必须在事件发布前保存成功。若保存成功但事件发布失败，旧画面可继续用，孤立新结果由 TTL 清理。`SurfaceRegistry` 若采用进程内实现，只供单实例开发；多副本必须使用共享实现并对同一 Surface 的 revision 更新提供原子条件写入，与现有 `SharedResultStore` 的部署约束一致。

### 5.2 前端消费

`packages/agent-ui/src/core/reducer.ts` 在 create 时记录原始 `threadId/runId` 和 revision；update 前检查所属 run、Profile 版本、Surface 是否存在、revision、组件白名单与 props。校验失败时保留旧 Surface 并记录 warning。`UiSurfacePart.vue` 在 `dataRef` 改变时取消旧请求；只允许最新请求完成后写入 `result`，并在加载失败时明确显示错误，不能把旧数据当成新数据。组件属性单独改变时也必须触发重新校验和重绘，不能只 watch `primary.type`。

这里的 “Data Model Update” 指新结果快照经 `dataRef` 切换；不新增 `data.update` 事件或浏览器端可变数据模型。若未来要逐行增量流，需另做顺序、重放、授权和数据一致性设计。

## 6. 交互流程

### 6.1 Chart 点击下钻

沿用现有 `drillDown` ViewHint：`ChartRenderer.vue` 产生事件，`UiSurfacePart.vue` 向上转发，宿主用 `useConversation.send` 发送追问，新 run 产生新结果和新 Surface。增加宿主集成示例，确认 `RichMessageView` 对事件继续向上透传。修正事件 `surfaceId`：当前 `ChartRenderer` 填的是组件 ID，应由 `UiSurfacePart` 使用真正的 `props.surface.surfaceId` 补齐。模板占位符找不到值时禁止发送空洞追问，展示可恢复提示；模板及属性均当作不可信文本，做长度限制和普通文本渲染。

### 6.2 Tree 节点展开

`TreeRenderer` 初次只显示根节点，待用户点击后展开已加载的下一层；点击有子节点的条目只修改本地展开集合，按 `id` 维护，键盘 Enter/Space 可操作，`aria-expanded` 反映状态。已加载节点的展开不会触发 Agent 请求，也不产生 `ui.surface.update`。若工具结果 `summary.truncated=true` 或节点声明 `hasChildren=true` 却没有已加载子节点，则显示“查看详情”；该按钮只在 ViewHint 为节点声明有效 `drillDown` 时可用，按同一追问机制获取新的对话结果。不要假装远端子节点已经展开。

### 6.3 其余组件点击

`Metric`、`EntityCard`、`Heatmap`、`RelationshipPath`、`EvidenceChain` 默认只读。若 ViewHint 显式给出可解析的 `drillDown`，渲染器可以在对应行/格/步骤上发出与 Chart 相同的追问事件；宿主仍走统一 `send`。本期最小验收要求 Chart 接通，其他类型的点击只有在各自的命中行与占位符规则实现并有契约样例后才开启；不显示无效的交互提示。

## 7. 分模块实施清单

1. **`mcp-contract`**：增加六种 `ViewHint`/`ViewMapping` 实现、Jackson subtype、1.2 JSON Schema；增加 Profile 1.1 的六类组件与 `revision`；更新版本常量、旧版本兼容逻辑、合法/非法 fixture 和 `docs/mcp-rich-result-contract.md`。
2. **`rich-ui-core`**：扩展 `PresentationValidator` 的字段类型和整批校验，扩展 `PresentationMapper`；增加 Surface Registry 与同 run `create/update` 服务方法；为 create/update 使用明确的运行时事件类型或受限工厂，不允许任意 `CustomRuntimeEvent` 绕开校验。
3. **两套 Runtime**：在 `agent-client` 与 `runtime-agentscope-v2` 的 `ui_render` 旁提供参数相同的 `ui_update(surfaceId, resultRef, viewId)`；都先经核心服务授权/校验，再发 `ui.surface.update`。事件映射和 AG-UI 翻译保持同形，并明确事件携带的 run 关联。
4. **`packages/agent-ui`**：按 Profile 版本校验六类 props；注册六个 Renderer；实现本地 Tree 展开和新版更新 revision；修正结果请求竞争与组件属性变更后的重绘；把统一 `drill-down` 冒泡至 SDK 宿主。
5. **`mcp-server` 测试工具及样例**：按第 8 节增加六个可调用工具和固定数据集。ViewHint mapping 必须对应数据字段；工具只生成受控声明，不生成 UI 代码；需要下钻的工具提供完整的 `resultMeta.attributes` 上下文，并校验查询参数。
6. **手工测试问句**：在《[测试问句](测试问句.md)》增加六类视图各一条自然语言问句，并在预期效果中列出对应工具、`viewId` 和可见结果；另加 Tree 的同 run 更新场景。问句随测试工具和 Renderer 一起验收，不把尚未实现的视图写成当前已可使用。

## 8. `mcp-server` 测试工具与返回数据

### 8.1 实现位置与共同约束

现有 `mcp-server` 通过 `@Component` + `@McpTool` 注册工具，工具返回 `Map<String,Object>` 形式的 `McpResult`；`McpResults` 统一填充 `specVersion`、`summary`、`presentation` 和 `resultMeta`。本期在 `mcp-server/src/main/java/com/ac/mcp/server/tool/` 下按业务域增加六个工具类，使用一个只在 `demo`/`test` 环境启用的 `PhaseTwoFixtureService` 提供固定快照。可以复用 `ActivityService` 等现有服务的查询语义，但下面的验收数据使用固定时间和 ID，不依赖 `LocalDate.now()`、随机数或外部 REST 服务。生产环境不注册这些演示工具；真实业务工具可按同一 ViewHint 契约逐步接入。

六个工具成功时统一返回：`specVersion: "1.2"`、`success: true`、对象数组 `data`、`summary{count,total,truncated,description,highlights}`、`presentation{mode:"RECOMMENDED",views:[一个 ViewHint]}` 和 `resultMeta{requestId,generatedAt,attributes}`。`McpResults` 当前硬编码 1.1，应新增受控的 1.2 构造入口；不能简单把所有旧工具的输出同时改成 1.2。`requestId`/`generatedAt` 可随调用变化，`data`、ViewHint 与测试用 `summary` 必须稳定。无匹配数据时返回 `success:true`、空 `data`、`mode:"NONE"`，不强行创建会被 `PresentationValidator` 拒绝的空 Surface；非法参数返回统一业务失败结构，不返回伪造的成功数据。

| 新工具名（建议类名） | 参数 | 返回用途与 ViewHint |
|---|---|
| `kg_activity_metrics` (`ActivityMetricsTool`) | `personId`，固定样例为 `person-001` | 活动总数、涉及城市数；`metric/single` |
| `kg_entity_cards` (`EntityCardsTool`) | `keyword`，样例为 `person` | 多张实体卡与文本边界；`entity_card/standard` |
| `kg_relation_tree` (`RelationTreeTool`) | `rootId`、`snapshot`=`base/expanded` | 多层树、前端本地展开、同 run 更新；`tree/hierarchy` |
| `kg_activity_heatmap` (`ActivityHeatmapTool`) | `personId` | 城市 × 活动类型计数；`heatmap/matrix` |
| `kg_relationship_path` (`RelationshipPathTool`) | `sourceId`、`targetId` | 有序关系路径；`relationship_path/ordered` |
| `kg_evidence_chain` (`EvidenceChainTool`) | `entityId` | 有序证据列表与来源文本；`evidence_chain/ordered` |

### 8.2 固定样例内容

以下 JSON 为各工具返回的 `data` 和 `presentation.views[0]` 的确定性内容；其余 envelope 字段按上节公共约束补齐。字段名要与 ViewHint 的 `mapping` 严格一致，`viewId` 在工具的 `base/expanded` 快照间保持不变。示例均是测试用虚构数据，不作为真实业务事实。

**`kg_activity_metrics(person-001)`**：

```json
{
  "data": [{"label":"活动总数","value":16,"unit":"次"},{"label":"涉及城市","value":3,"unit":"个"}],
  "view": {"id":"activity-metrics","type":"metric","subType":"single","title":"活动概览","mapping":{"label":"label","value":"value","unit":"unit"},"options":{"limit":12}}
}
```

`summary.count=2`、`summary.total=2`；`resultMeta.attributes.personId="person-001"`。指标由同一套固定活动 fixture 聚合，后续调整活动样例时须同步保持计数一致。

**`kg_entity_cards(person)`**：

```json
{
  "data": [{"id":"person-001","name":"张三","kind":"PERSON","summary":"示例人员"},{"id":"person-002","name":"李四","kind":"PERSON","summary":"示例关联人员"}],
  "view": {"id":"entity-cards","type":"entity_card","subType":"standard","title":"实体检索结果","mapping":{"id":"id","name":"name","kind":"kind","summary":"summary"},"options":{"limit":50,"showSummary":true}}
}
```

`summary.count=2`、`summary.total=2`；`resultMeta.attributes.keyword="person"`。返回顺序按 ID 固定，文本作为纯文本渲染。

**`kg_relation_tree(org-root, base)`**：

```json
{
  "data": [{"nodeId":"org-root","parentNodeId":null,"nodeName":"示例机构","hasChildren":true},{"nodeId":"org-dev","parentNodeId":"org-root","nodeName":"研发部","hasChildren":true}],
  "view": {"id":"org-tree","type":"tree","subType":"hierarchy","title":"组织结构","mapping":{"id":"nodeId","parentId":"parentNodeId","label":"nodeName","hasChildren":"hasChildren"},"options":{"limit":500},"drillDown":{"enabled":true,"dimension":"nodeId","label":"查看子节点详情","promptTemplate":"展示 {rootId} 下 {nodeId} 的完整子节点"}}
}
```

`summary.count=2`、`summary.total=3`、`summary.truncated=true`；`resultMeta.attributes` 包含 `rootId="org-root"`、`snapshot="base"`。`org-dev` 宣称有子节点但本快照尚未加载；因 ViewHint 显式声明了 `drillDown`，其“查看详情”可发起新对话。**`kg_relation_tree(org-root, expanded)`** 保持同一 ViewHint，仅把 `data` 增加 `{"nodeId":"org-data","parentNodeId":"org-dev","nodeName":"数据组","hasChildren":false}`；此时 `summary.count=3`、`summary.total=3`、`summary.truncated=false`、`resultMeta.attributes.snapshot="expanded"`。两个结果须在同一 run 中调用并保存为不同的 `resultRef`，先 `ui_render(base)`，再 `ui_update(surfaceId, expandedResultRef, "org-tree")`。仅调用两个 MCP 工具不会自动发出 Surface 更新事件。

### 8.3 工具测试与现有工具回归

为六个工具增加单元测试：固定参数返回上述行、映射和 summary；未知 ID 返回空成功结果；缺失/非法参数返回业务失败；`base/expanded` 的树快照满足父子关系且不修改旧快照。将六份完整 `McpResult 1.2` JSON 加入 `mcp-contract` 的合法 fixture，与工具返回的 JSON 做同一 schema 校验。增加一项启用 `demo`/`test` Profile 的 MCP 工具发现与调用集成测试；当前 `McpServerIntegrationTest` 标记为 `@Disabled` 且只有空测试方法，不能作为交付验收依据。

继续回归 `kg_activity_statistics` → Chart 点击追问 → `kg_list_activity` 的现有路径。新工具不取代旧工具，`McpResults` 的版本入口应确保现有工具仍输出契约有效的 1.1 结果。端到端测试还要覆盖 `kg_relation_tree` 两次结果经 `ui_render/ui_update` 产生 create/update 事件，浏览器读取新 `dataRef` 后显示第三级节点。

## 9. 验收与测试

| 层级 | 必测场景 |
|---|---|
| 契约 | 六类合法 fixture；缺字段/错类型、重复 ID、孤儿或环形 Tree、非连续 Path/Chain、重复 Heatmap 坐标、越界 limit、非法 props、未知版本均拒绝；1.0/1.1 旧样例继续通过 |
| 核心 | 六类映射、授权读取、原子更新、跨 tenant/user/thread/run 拒绝、旧 `dataRef` 不变、更新失败不发事件、revision 竞争 |
| Runtime | 两套 `ui_render/ui_update` 产生相同 Profile 内容；`ui.surface.create` 必先于同 run update；事件不含完整业务数据 |
| 前端 | 六类渲染、空值/长文本、过期/403/404、未知 Profile 降级、旧请求晚返回不覆盖新结果、组件 props 变更重绘、旧/重复/缺号 update 不破坏当前 Surface |
| 交互 | Chart 点击只发送一次追问且带正确 `surfaceId`；Tree 展开不请求后端；未加载节点仅走显式详情追问；键盘操作可用 |
| 集成 | 同一次 run：保存 R1 → create → 保存 R2 → update → 浏览器读 R2；另一 run 更新旧 Surface 被拒；新 run 点击下钻生成新的 Surface，不原地覆盖旧 Surface |
| MCP 工具 | 六个新工具可发现、可调用；返回完整 1.2 envelope 且与第 8 节固定样例及 schema 一致；`base/expanded` 可完成同 run 更新；旧活动统计/下钻工具仍通过 1.1 回归 |
| 测试问句 | 《测试问句》第 15 节的六条视图问句能触发对应 MCP 工具和 `ui_render`；显示标题、行数及关键数值与固定样例一致；Tree 更新问句另验证 `ui_update` 事件 |

完成顺序：先定契约与 fixture，再实现核心校验和更新服务，再接通两套 Runtime，最后实现前端渲染与宿主交互。每一步均用同一份契约 fixture 验证 Java 与 TypeScript 消费者，避免两端白名单漂移。

## 10. 《测试问句》的第二阶段覆盖

《[测试问句](测试问句.md)》第 15 节提供第二阶段手工验收入口。输入保持普通用户的提问方式，仅说明希望看到的展示形式；对应工具、`resultRef + viewId`、`ui_render` 和预期数据写在预期效果中供测试人员核对。六条问句分别覆盖 `activity-metrics`、`entity-cards`、`org-tree`、`activity-heatmap`、`person-org-path` 和 `person-evidence`。观察点是**展示预期组件**，不是所有组件都画成统计图。

这些问句仅在第 8 节的演示工具、`McpResult 1.2` 契约、Profile 1.1 和前端 Renderer 均交付并启用 `demo`/`test` 环境后可执行。Tree 的 `base → expanded` 原地更新要求同一 run 内调用两次 MCP 工具，再调用 `ui_update`；若模型没有稳定执行指定顺序，使用集成测试直接驱动调用链验收，不以自然语言问句作为唯一判断依据。
